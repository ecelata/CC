01 — Mapa completo de recursos para practicar
Cómo elegir el entorno correcto según tu objetivo
▼

No existe un único entorno ideal para aprender AWS. La clave es elegir el correcto según lo que querés practicar: si necesitás experimentar con infraestructura real usá el Free Tier; si querés iterar rápido sin preocuparte por costos usá LocalStack; si preferís aprender con guía usá Skill Builder. Lo ideal es combinar los tres.

Configuración de seguridad obligatoria antes de empezar
1
Activar MFA en la cuenta root inmediatamente
La cuenta root nunca debe usarse para el día a día. Activá MFA, guardá las credenciales en un lugar seguro y nunca generés Access Keys para root.
2
Crear un usuario IAM para uso diario
Usuario con permisos específicos (no AdministratorAccess para todo). Para practicar podés usar PowerUserAccess pero en producción siempre el principio de mínimo privilegio.
3
Configurar alerta de billing en $5 USD desde el día 1
Billing → Budgets → Create Budget → $5 USD → email alert. Si algo sale mal o dejaste un recurso corriendo, el email llega antes de que la factura sorprenda.
4
Elegir la región correcta para practicar
Para latencia desde Argentina: us-east-1 (N. Virginia) o sa-east-1 (São Paulo). sa-east-1 tiene algunos servicios más caros pero es la más cercana. Para practicar IaC y arquitecturas, us-east-1 tiene más disponibilidad de servicios.

04 — Emulación local con LocalStack
AWS completo en tu laptop — sin cuenta, sin costo, sin riesgo
▼

LocalStack es un emulador de AWS que corre localmente en Docker. Simula los servicios más importantes de AWS con la misma API — podés usar AWS CLI, SDKs y Terraform exactamente igual que con AWS real, pero todo corre en tu máquina sin ningún costo ni cuenta de AWS necesaria.

Setup en 5 minutos
Cómo instalar y usar LocalStack — de cero a S3 y Lambda corriendo localmente
Requiere Docker instalado en la máquina
▼
Paso 1 — Instalar LocalStack
Terminal — instalación con pip o docker
# Opción A: con pip (recomendado)
pip install localstack

# Opción B: con docker compose (más control)
# Crear archivo docker-compose.yml:
version: "3.8"
services:
  localstack:
    image: localstack/localstack
    ports:
      - "127.0.0.1:4566:4566"
    environment:
      - SERVICES=s3,lambda,dynamodb,sqs,iam,ec2
      - DEBUG=1
    volumes:
      - "/var/run/docker.sock:/var/run/docker.sock"

# Iniciar LocalStack:
localstack start          # con pip
docker compose up         # con docker compose
Paso 2 — Configurar AWS CLI para apuntar a LocalStack
# Configurar credenciales "falsas" (LocalStack las acepta igual)
aws configure
AWS Access Key ID: test
AWS Secret Access Key: test
Default region name: us-east-1

# Todos los comandos con --endpoint-url apuntando a LocalStack:
aws s3 mb s3://mi-bucket --endpoint-url=http://localhost:4566
aws s3 ls --endpoint-url=http://localhost:4566
aws s3 cp archivo.txt s3://mi-bucket/ --endpoint-url=http://localhost:4566

# Tip: crear alias para no repetir el endpoint-url
alias awslocal='aws --endpoint-url=http://localhost:4566'
awslocal s3 mb s3://mi-bucket     # mucho más cómodo
Paso 3 — Ejemplo: crear función Lambda en LocalStack
# 1. Crear el código de la función (hello.py)
def handler(event, context):
    return {'statusCode': 200, 'body': 'Hello from LocalStack!'}

# 2. Empaquetar en ZIP
zip function.zip hello.py

# 3. Crear la Lambda en LocalStack
awslocal lambda create-function \
  --function-name mi-funcion \
  --runtime python3.11 \
  --handler hello.handler \
  --zip-file fileb://function.zip \
  --role arn:aws:iam::000000000000:role/lambda-role

# 4. Invocar la Lambda
awslocal lambda invoke \
  --function-name mi-funcion \
  output.json && cat output.json
Servicios disponibles en LocalStack Community (gratis): S3, Lambda, DynamoDB, SQS, SNS, API Gateway, IAM, CloudFormation, SSM, Secrets Manager, EventBridge, Kinesis y más de 60 servicios. Los servicios más avanzados (EKS, RDS con Multi-AZ real) requieren el plan Pro ($35/mes).
Terraform + LocalStack
Practicar IaC con Terraform sin gastar un centavo — el workflow ideal para development
El combo más potente para aprender IaC sin riesgo
▼
main.tf — Terraform apuntando a LocalStack
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

# Provider apuntando a LocalStack
provider "aws" {
  region                      = "us-east-1"
  access_key                  = "test"
  secret_key                  = "test"
  skip_credentials_validation = true
  skip_metadata_api_check     = true
  skip_requesting_account_id  = true

  endpoints {
    s3       = "http://localhost:4566"
    dynamodb = "http://localhost:4566"
    lambda   = "http://localhost:4566"
    iam      = "http://localhost:4566"
  }
}

# Crear un bucket S3
resource "aws_s3_bucket" "mi_bucket" {
  bucket = "mi-bucket-de-practica"
}

# Crear una tabla DynamoDB
resource "aws_dynamodb_table" "mi_tabla" {
  name         = "Productos"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "ProductId"

  attribute {
    name = "ProductId"
    type = "S"
  }
}

# Desplegar:
# terraform init && terraform plan && terraform apply

05 — IaC: CloudFormation · CDK · Terraform
Las tres herramientas de Infraestructura como Código — cuándo usar cada una y ejemplos comentados
▼

La infraestructura que no está en código no existe. Cualquier recurso AWS creado manualmente desde la consola es un riesgo operativo — no se puede reproducir, versionar ni auditiar. Las tres herramientas de IaC cubren distintos perfiles y necesidades.

Cuándo usar cada una
CloudFormation vs. CDK vs. Terraform — la guía de selección
Cada herramienta tiene su lugar — no son excluyentes
▼
CloudFormationAWS CDKTerraform
LenguajeYAML / JSONPython, TypeScript, Java, C# (código real)HCL (HashiCorp Config Language)
Curva de aprendizajeMedia — verboso pero predecibleAlta al inicio, luego muy productivoBaja — HCL es muy legible
Multi-cloudSolo AWSSolo AWS (con adaptadores)AWS + Azure + GCP + cualquier provider

Ideal paraEquipos 100% AWS, infra estable, compliance estrictoDesarrolladores que prefieren código sobre YAML, proyectos complejosMulti-cloud, equipos DevOps, proyectos donde la infra puede moverse de proveedor

CloudFormation
Template completo comentado — VPC + EC2 + Security Group
El primer template que todo arquitecto AWS debe saber leer y escribir
▼
template.yaml — VPC + EC2 + Security Group
AWSTemplateFormatVersion: '2010-09-09'
Description: 'VPC con EC2 de práctica'

Parameters:
  InstanceType:
    Type: String
    Default: t2.micro
    AllowedValues: [t2.micro, t3.micro]
    Description: Tipo de instancia EC2

Resources:

  # 1. La red privada virtual
  MiVPC:
    Type: AWS::EC2::VPC
    Properties:
      CidrBlock: '10.0.0.0/16'
      EnableDnsHostnames: true
      Tags:
        - Key: Name
          Value: mi-vpc-practica

  # 2. Subred pública donde vivirá el EC2
  SubredPublica:
    Type: AWS::EC2::Subnet
    Properties:
      VpcId: !Ref MiVPC
      CidrBlock: '10.0.1.0/24'
      AvailabilityZone: !Select [0, !GetAZs '']
      MapPublicIpOnLaunch: true

  # 3. Internet Gateway — la puerta hacia internet
  IGW:
    Type: AWS::EC2::InternetGateway
  AttachIGW:
    Type: AWS::EC2::VPCGatewayAttachment
    Properties:
      VpcId: !Ref MiVPC
      InternetGatewayId: !Ref IGW

  # 4. Route table que dirige el tráfico al IGW
  RouteTable:
    Type: AWS::EC2::RouteTable
    Properties:
      VpcId: !Ref MiVPC
  DefaultRoute:
    Type: AWS::EC2::Route
    Properties:
      RouteTableId: !Ref RouteTable
      DestinationCidrBlock: '0.0.0.0/0'
      GatewayId: !Ref IGW
  SubnetRouteAssoc:
    Type: AWS::EC2::SubnetRouteTableAssociation
    Properties:
      SubnetId: !Ref SubredPublica
      RouteTableId: !Ref RouteTable

  # 5. Security Group — solo puerto 22 (SSH) y 80 (HTTP)
  MiSG:
    Type: AWS::EC2::SecurityGroup
    Properties:
      GroupDescription: SG para EC2 de practica
      VpcId: !Ref MiVPC
      SecurityGroupIngress:
        - IpProtocol: tcp
          FromPort: 22
          ToPort: 22
          CidrIp: '0.0.0.0/0'  # En prod: restringir a tu IP
        - IpProtocol: tcp
          FromPort: 80
          ToPort: 80
          CidrIp: '0.0.0.0/0'

  # 6. La instancia EC2
  MiEC2:
    Type: AWS::EC2::Instance
    Properties:
      InstanceType: !Ref InstanceType
      ImageId: ami-0c02fb55956c7d316  # Amazon Linux 2 en us-east-1
      SubnetId: !Ref SubredPublica
      SecurityGroupIds: [!Ref MiSG]
      UserData:  # Script que corre al iniciar
        Fn::Base64: |
          #!/bin/bash
          yum update -y
          yum install -y httpd
          systemctl start httpd
          echo "<h1>Hola desde CloudFormation</h1>" > /var/www/html/index.html

Outputs:
  PublicIP:
    Description: IP publica del EC2
    Value: !GetAtt MiEC2.PublicIp
Cómo desplegarlo
# Desde AWS CLI:
aws cloudformation create-stack \
  --stack-name mi-stack-practica \
  --template-body file://template.yaml \
  --parameters ParameterKey=InstanceType,ParameterValue=t2.micro

# Ver estado del stack:
aws cloudformation describe-stacks --stack-name mi-stack-practica

# Eliminar todo al terminar (¡importante para no generar costos!):
aws cloudformation delete-stack --stack-name mi-stack-practica

Ejemplo comentado — S3 + CloudFront + política de bucket (hosting estático)
Un caso de uso real y frecuente explicado línea a línea
▼
main.tf — Hosting de sitio estático en S3 + CloudFront
provider "aws" {
  region = "us-east-1"
}

# El bucket S3 donde viven los archivos del sitio
resource "aws_s3_bucket" "sitio" {
  bucket = "mi-sitio-estatico-unico-12345"
}

# Configurar el bucket para hosting web estático
resource "aws_s3_bucket_website_configuration" "sitio" {
  bucket = aws_s3_bucket.sitio.id
  index_document { suffix = "index.html" }
  error_document { key    = "error.html"  }
}

# Deshabilitar el bloqueo de acceso público (necesario para hosting)
resource "aws_s3_bucket_public_access_block" "sitio" {
  bucket                  = aws_s3_bucket.sitio.id
  block_public_acls       = false
  block_public_policy     = false
  ignore_public_acls      = false
  restrict_public_buckets = false
}

# Política que permite lectura pública de los archivos
resource "aws_s3_bucket_policy" "sitio" {
  bucket = aws_s3_bucket.sitio.id
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect    = "Allow"
      Principal = "*"
      Action    = "s3:GetObject"
      Resource  = "${aws_s3_bucket.sitio.arn}/*"
    }]
  })
}

# CloudFront distribution que sirve el contenido de S3
resource "aws_cloudfront_distribution" "cdn" {
  enabled             = true
  default_root_object = "index.html"

  origin {
    domain_name = aws_s3_bucket_website_configuration.sitio.website_endpoint
    origin_id   = "s3-origin"
    custom_origin_config {
      http_port              = 80
      https_port             = 443
      origin_protocol_policy = "http-only"
    }
  }

  default_cache_behavior {
    viewer_protocol_policy = "redirect-to-https"
    allowed_methods        = ["GET", "HEAD"]
    cached_methods         = ["GET", "HEAD"]
    target_origin_id       = "s3-origin"
    forwarded_values {
      query_string = false
      cookies { forward = "none" }
    }
  }

  restrictions {
    geo_restriction { restriction_type = "none" }
  }

  viewer_certificate {
    cloudfront_default_certificate = true
  }
}

# Output: la URL de CloudFront para acceder al sitio
output "url_sitio" {
  value = "https://${aws_cloudfront_distribution.cdn.domain_name}"
}

EC2 — Cómputo
Los ejercicios de EC2 que más enseñan — de instancia básica a Auto Scaling
5 ejercicios progresivos para dominar el cómputo en AWS
▼
1
Levantar una instancia t2.micro y conectarse por SSH
Crear Key Pair, Security Group con puerto 22, lanzar la instancia, conectarse con ssh -i mi-key.pem ec2-user@IP_PUBLICA. Instalar nginx y ver la web en el navegador. Tiempo: 30 minutos.
2
Crear una AMI personalizada desde la instancia configurada
Con nginx instalado, crear una AMI desde la instancia. Lanzar una segunda instancia desde la AMI — debe tener nginx ya instalado sin ejecutar ningún script. Entiende el concepto de imagen de máquina.
3
Application Load Balancer con 2 instancias en distintas AZ
Crear 2 instancias en AZ distintas (us-east-1a y us-east-1b), crear un Target Group, crear un ALB. Verificar que el ALB distribuye el tráfico entre las dos. Apagar una — el ALB debe dejar de enviarle tráfico automáticamente. Concepto clave: alta disponibilidad.
4
Auto Scaling Group que escala según carga de CPU
Launch Template + ASG con mínimo 2, máximo 6 instancias. Crear alarma de CloudWatch al 70% CPU que dispara la política de escalado. Usar stress para generar carga y ver cómo el ASG agrega instancias automáticamente. Concepto clave: escalado horizontal.
5
Todo el stack anterior con CloudFormation o Terraform
Definir el VPC, subredes, SG, ALB, ASG y políticas de escalado en un template IaC. El objetivo: destruirlo con un comando y volver a crearlo idéntico en 5 minutos. Concepto clave: infraestructura reproducible.
S3 — Almacenamiento
Los 4 casos de uso de S3 que aparecen en toda arquitectura AWS
▼
🌐
Hosting estático
Crear un bucket, subir index.html, habilitar el hosting estático, configurar política de acceso público. Opcional: poner CloudFront delante para HTTPS. Todo una arquitectura de frontend sin servidores.
📥
Upload con pre-signed URLs
Generar URLs firmadas temporales con Python (boto3) para que usuarios suban archivos directamente a S3 sin pasar por el backend. Patrón fundamental en apps web modernas.
⚡
Trigger Lambda con S3 Events
Configurar que cada archivo subido a un bucket dispare una función Lambda automáticamente. Usar para procesamiento de imágenes, extracción de datos, notificaciones. El patrón de procesamiento asincrónico más usado.
🔒
Lifecycle + Glacier
Configurar reglas de ciclo de vida: archivos creados hace más de 90 días → S3 Standard-IA. Más de 365 días → S3 Glacier. Reducción automática de costos de storage sin intervención manual.
VPC — Redes
Construir una VPC con 3 capas — la arquitectura de red más usada en AWS enterprise
Subred pública + privada + NAT Gateway — el patrón de referencia
▼

La arquitectura de VPC más usada en producción tiene 3 capas: subred pública (ALB, bastion host), subred privada (servidores de aplicación), subred de base de datos (RDS sin acceso desde internet).

Arquitectura de referencia — 3 capas en 2 AZ
VPC: 10.0.0.0/16
├── Subred Pública     10.0.1.0/24 (AZ-a)  → ALB, Bastion Host, NAT GW
├── Subred Pública     10.0.2.0/24 (AZ-b)  → ALB secundario
├── Subred Privada     10.0.3.0/24 (AZ-a)  → EC2 App Servers
├── Subred Privada     10.0.4.0/24 (AZ-b)  → EC2 App Servers (réplica)
├── Subred BD          10.0.5.0/24 (AZ-a)  → RDS Primary
└── Subred BD          10.0.6.0/24 (AZ-b)  → RDS Standby (Multi-AZ)

Internet Gateway  → solo subredes públicas
NAT Gateway       → permite salida a internet desde subredes privadas (updates, etc.)
Security Groups:
  ALB-SG:     entrada 80/443 desde 0.0.0.0/0
  App-SG:     entrada 8080 solo desde ALB-SG
  DB-SG:      entrada 5432 solo desde App-SG
Por qué esta arquitectura: El ALB está en la subred pública y recibe tráfico de internet. Los servidores de aplicación están en la subred privada — no tienen IP pública, solo reciben tráfico del ALB. La base de datos está en la subred de BD — solo los servidores de aplicación pueden conectarse. Tres capas de seguridad.

boto3 — operaciones más frecuentes comentadas
import boto3
import json
from datetime import datetime

── S3 ──────────────────────────────────────────────
s3 = boto3.client('s3')

# Subir archivo
s3.upload_file('archivo.txt', 'mi-bucket', 'carpeta/archivo.txt')

# Leer archivo como texto
response = s3.get_object(Bucket='mi-bucket', Key='datos.json')
datos = json.loads(response['Body'].read())

# Generar URL pre-firmada para subida (válida 1 hora)
url = s3.generate_presigned_url(
    'put_object',
    Params={'Bucket': 'mi-bucket', 'Key': 'uploads/imagen.jpg'},
    ExpiresIn=3600
)

── DynamoDB ─────────────────────────────────────────
ddb = boto3.resource('dynamodb')
tabla = ddb.Table('Productos')

# Insertar item
tabla.put_item(Item={
    'ProductId': 'prod-001',
    'Nombre': 'Laptop',
    'Precio': 1200,
    'Timestamp': datetime.now().isoformat()
})

# Obtener item por clave
item = tabla.get_item(Key={'ProductId': 'prod-001'})
print(item.get('Item'))

# Query (buscar por índice)
from boto3.dynamodb.conditions import Key
items = tabla.query(
    KeyConditionExpression=Key('ProductId').eq('prod-001')
)

── Lambda desde Lambda (invocar otra función) ───────
lambda_client = boto3.client('lambda')
response = lambda_client.invoke(

    InvocationType='Event',  # 'Event' = asincrónico, 'RequestResponse' = sincrónico
    Payload=json.dumps({'key': 'value'}).encode()

08 — Roadmap de práctica — de cero a Solutions Architect
El camino de 12 semanas para ir de la consola de AWS a proponer arquitecturas como un experto
▼
Las 12 semanas
Plan progresivo de práctica — 4–6 horas semanales
Diseñado para el consultor cloud que trabaja full-time y practica en paralelo
▼
1-2
Semanas 1–2: Fundamentos — Consola, IAM y S3
Crear cuenta con Free Tier. Configurar MFA y billing alert. Crear usuario IAM con MFA. Explorar la consola. Crear bucket S3, subir archivos, habilitar versionado, configurar hosting estático. Entorno: Free Tier + LocalStack para S3.
3-4
Semanas 3–4: Cómputo — EC2 y redes básicas
Crear VPC con subred pública. Lanzar instancia EC2 t2.micro. Conectar por SSH. Instalar nginx. Crear Security Groups. Crear AMI propia. Todo desde CloudFormation al final de la semana.
5-6
Semanas 5–6: Alta disponibilidad — ALB + Auto Scaling
Multi-AZ con 2 subredes públicas. Application Load Balancer. Auto Scaling Group con política de CPU. CloudWatch alarm. Probar failover apagando instancias. Entender que el ALB hace health checks y saca las instancias enfermas.
7-8
Semanas 7–8: Serverless — Lambda + API Gateway + DynamoDB
API REST completa sin servidores: API Gateway → Lambda (Python) → DynamoDB. CRUD completo. Probar desde curl o Postman. Agregar authorizer. Desplegar todo con CDK.
9-10
Semanas 9–10: Bases de datos — RDS Multi-AZ + ElastiCache
RDS PostgreSQL en subred privada. Multi-AZ enabled. Conectar desde EC2 (no desde tu laptop). ElastiCache Redis para cachear consultas frecuentes. Medir la diferencia de latencia con y sin caché.
11-12
Semanas 11–12: Proyecto integrador — arquitectura completa con Terraform
Construir una aplicación completa con todos los conceptos: VPC 3 capas, ALB, EC2 en ASG, RDS Multi-AZ, S3 para estáticos, CloudFront, CloudWatch, IAM roles. Todo el stack definido en Terraform. Un comando lo crea, un comando lo destruye. Este es el portfolio que presentás ante Gerardo.
El objetivo real del roadmap
"Al terminar estas 12 semanas, podés sentarte con cualquier CTO o arquitecto de un cliente y decir: 'He construido y destruido esta arquitectura docenas de veces con Terraform. Sé exactamente qué falla, cómo se comporta bajo carga y cuánto cuesta.' Eso no es teoría — es experiencia."
