El Universo de los Workloads
Cómo cada hyperscaler, hypervisor y solución de backup define, mide y licencia una "carga de trabajo"
Edgardo Mauricio Celata
Analista Sr. Infraestructura y Cloud
⚡ Por qué este documento existe
La palabra "workload" es probablemente el término más sobrecargado de toda la infraestructura moderna. Para AWS es una unidad lógica de arquitectura que se revisa con un framework. Para VMware/Broadcom, desde 2024, ya casi no importa — lo que importa es el core físico del host. Para Nutanix, la licencia se basa en capacidad de cluster, no en cuántas VMs corren arriba. Para Veeam, un workload es literalmente la unidad de facturación: una VM, un servidor físico, una base de datos o un buzón de Microsoft 365 — todos cuentan igual. Entender estas diferencias no es un ejercicio académico: definen cómo se diseña una arquitectura, cómo se la protege con backup y air-gap, y cuánto cuesta cada decisión.

El Concepto: ¿Qué es un Workload?
4 definiciones base ▼
Antes de comparar cómo lo factura cada vendor, hay que entender que "workload" tiene múltiples significados simultáneos y válidos según quién lo use: el arquitecto, el ingeniero de virtualización, el administrador de backup o el FinOps.
Definiciones por disciplina
Definición Arquitectónica
la más amplia Concepto
▼
En el sentido más amplio usado por arquitectos cloud, un workload es una colección de recursos y código que entrega valor de negocio: una aplicación completa, un componente de esa aplicación, o un proceso técnico que la soporta (un pipeline de datos, una API, un sistema de colas). No es una sola máquina virtual ni un solo servidor — es la unidad lógica que se diseña, se revisa y se factura como conjunto.
📋 Ejemplos de un workload bajo esta definición
  • Un e-commerce completo: frontend + backend + base de datos + CDN + cola de pedidos
  • Un pipeline de ETL: extracción + transformación + carga + orquestador
  • Un sistema de autenticación: servicio de identidad + base de usuarios + cache de sesiones
📌 Esta es la definición que usan AWS, Azure y GCP en sus Well-Architected Frameworks — y es completamente distinta a cómo VMware o Veeam usan la misma palabra para facturar.
Definición de Virtualización
la más técnica Concepto
▼
Para un administrador de virtualización (VMware, Hyper-V, Nutanix, Proxmox), un workload es simplemente una VM en ejecución sobre un host físico, consumiendo CPU, RAM y storage de ese host. Es la unidad que el hypervisor agenda, migra (vMotion/Live Migration) y protege con HA. No importa qué corre dentro de la VM — para el hypervisor, una VM de SQL Server crítico y una VM de testing son ambas "un workload" hasta que se les asignan políticas distintas.
📋 Lo que cuenta como workload aquí
  • Una máquina virtual completa (vCPU + vRAM + vDisk)
  • Un contenedor o pod (en plataformas con soporte nativo de contenedores)
  • Una VM bare-metal gestionada (en Nutanix AHV o casos similares)
Definición de Backup / Protección de Datos
la más comercial Concepto
▼
Para el mundo del backup (Veeam, Rubrik, Cohesity, Commvault), un workload es la unidad protegible mínima que se factura. Esta es la definición más amplia de todas en términos de variedad de objetos: puede ser una VM, un servidor físico, un endpoint, una base de datos, un buzón de Microsoft 365, un bucket de S3 o un namespace de Kubernetes. Cada uno de esos objetos —sin importar su tamaño o complejidad interna— cuenta como "1 workload" a la hora de licenciar.
📋 Objetos que típicamente cuentan como 1 workload
  • 1 máquina virtual (VMware, Hyper-V, Nutanix AHV, KVM)
  • 1 servidor físico (Windows o Linux)
  • 1 instancia de base de datos (SQL Server, Oracle, PostgreSQL)
  • 1 buzón de Microsoft 365 o 1 sitio de SharePoint
  • 1 cuenta cloud completa (AWS, Azure, GCP) en algunos modelos de nicho
⚠️ Esta es la definición que más confunde a los compradores: "tengo 50 VMs" no es lo mismo que "tengo 50 workloads" si además hay bases de datos, buzones o servidores físicos sueltos que cada vendor de backup cuenta por separado.
Definición FinOps / de Negocio
la más práctica Concepto
▼
Desde la óptica de costos (FinOps), un workload es la unidad mínima a la que se le puede asignar un dueño, un centro de costo y un nivel de criticidad de negocio. Esta definición es funcional, no técnica: lo que importa es poder responder "¿quién es responsable de esto?" y "¿cuánto cuesta mantenerlo corriendo?". Un mismo workload técnico (ej. un cluster de Kubernetes) puede contener decenas de "workloads de negocio" (cada microservicio con su propio dueño y presupuesto).
📋 Atributos que un workload de negocio necesita tener
  • Un dueño (persona o equipo responsable)
  • Un tag de centro de costo o proyecto
  • Un nivel de criticidad (Tier 0/1/2/3, define RPO/RTO esperado)
  • Un ambiente (producción, staging, desarrollo)
💡 En preventa, esta es la definición más útil para conversar con el cliente: preguntar "¿cuántos workloads de negocio tenés?" es mejor que preguntar "¿cuántas VMs tenés?", porque revela presupuesto, criticidad y quién decide.

Hyperscalers — AWS, Azure, GCP
3 frameworks ▼
Los tres grandes cloud públicos no "licencian" workloads como tales — cobran por recursos consumidos. Pero cada uno tiene un Well-Architected Framework que define al workload como la unidad de revisión arquitectónica, y eso moldea cómo se diseñan, documentan y optimizan las cargas en cada plataforma.
AWS
AWS Well-Architected Framework
Consumo
▼
AWS fue el primer hyperscaler en publicar un framework formal, y es el más detallado y tool-driven de los tres. Define al workload como "una colección de recursos y código que entrega valor de negocio", aplicable tanto a una aplicación completa como a un componente técnico específico. El AWS Well-Architected Tool, gratuito en la consola, permite evaluar cada workload contra 6 pilares y registrar mejoras a lo largo del tiempo.
PilaresExcelencia Operacional, Seguridad, Confiabilidad, Eficiencia de Rendimiento, Optimización de Costos, Sostenibilidad (agregado en 2021)
Unidad de revisión1 workload = 1 aplicación o componente evaluado independientemente
HerramientaAWS Well-Architected Tool (gratuita, en la consola)
DiferencialBiblioteca de "Lenses" especializados por tipo de carga: ML, IoT, SaaS, Serverless, etc.
💡 La fortaleza de AWS es la profundidad técnica: cada Lens agrega preguntas específicas para ese tipo de workload, en lugar de aplicar las mismas 6 preguntas genéricas a todo.
Microsoft Azure
Azure Well-Architected Framework
Consumo
▼
Azure es explícitamente workload-centric: el framework se aplica a una aplicación o plataforma específica, no al tenant completo de la organización. En 2023 Microsoft restructuró su modelo de 6 a 5 pilares, absorbiendo la sostenibilidad dentro de los pilares existentes en lugar de tratarla como un pilar separado (a diferencia de AWS). Los equipos de plataforma suelen correr revisiones de forma rotativa, evaluando siempre al menos un workload del portfolio en cualquier momento dado.
PilaresConfiabilidad, Seguridad, Optimización de Costos, Excelencia Operacional, Eficiencia de Rendimiento
Unidad de revisión1 workload = 1 aplicación o plataforma específica (nunca el tenant completo)
DiferencialFuerte en gobernanza y soporte de escenarios híbridos (Azure Arc, Azure Local)
📌 La definición de Azure es la más explícita en remarcar el límite: revisar "todo Azure" no es una revisión Well-Architected válida — siempre hay que acotar a un workload puntual.
Google Cloud Platform
GCP — Enfoque de Workload
Consumo
▼
GCP comparte la misma filosofía general de "workload como unidad de revisión arquitectónica" que sus competidores, con un sesgo natural hacia cargas de datos y Machine Learning (BigQuery, Vertex AI), reflejo de su origen como compañía de datos. GCP no facilita un nombre de marca tan publicitado como "Well-Architected" para su framework equivalente, pero aplica los mismos principios de revisión por pilares.
Fortaleza distintivaWorkloads de datos y ML — BigQuery, Vertex AI, Dataflow
Modelo de costosEgress reducido significativamente en 2025-2026 frente a AWS/Azure, relevante para workloads con alta transferencia de datos saliente
Always FreeIncluye f1-micro, 5GB de Cloud Storage y 1GB de consultas BigQuery/mes sin vencimiento — útil para workloads chicos que se mantienen chicos

Hypervisors — Cómo licencian el workload
3 modelos ▼
Acá el workload deja de ser un concepto de diseño y se vuelve una unidad de facturación directa. El quiebre de 2024 (Broadcom) cambió completamente las reglas del juego para todo el mercado de virtualización.
VMware / Broadcom
VCF / VVF — Licenciamiento Per-Core
el gran quiebre de 2024 Per-Core
▼
Desde la adquisición de Broadcom (completada en diciembre 2023), VMware dejó de pensar en "workloads" como unidad de licencia. El modelo nuevo es 100% per-core: se licencian todos los núcleos físicos de CPU de todos los hosts ESXi en el alcance, sin importar cuántas VMs corren arriba, sin licenciamiento por capacidad, sin exclusión para servidores de test/desarrollo. El portfolio de más de 160 productos se redujo a solo 4 bundles de suscripción, y las licencias perpetuas fueron discontinuadas por completo.
Mínimo por CPU16 cores por CPU física (un CPU de 8 o 12 cores se factura igual a 16)
Mínimo por instancia72 cores mínimo por licencia, además del mínimo de 16/CPU
Modelo100% suscripción — sin perpetuas, sin grace period al vencer
VCF incluyevSphere (cómputo), vCenter (gestión), Aria Suite, Tanzu Kubernetes Grid, NSX (redes)
VVF vs VCFVVF cuesta 30-40% menos por core, pero sin NSX ni stack de gobernanza completo
vSAN incluidoVVF: 0.25 TiB por core · VCF: 1 TiB por core (licencia separada desde nov. 2024)
⚠️ El mínimo de 16 cores/CPU infla la factura entre 20% y 40% en hosts con CPUs de 8-12 cores reales, que eran comunes hasta hace pocos años. Las primeras cotizaciones de Broadcom suelen abrir en 2x-5x el costo anterior; con negociación bajan a 1.3x-2x.
💡 Defaultear a VCF "porque es el estándar enterprise" sin un análisis de utilización real puede costarle a una empresa grande entre 500K y 2M+ USD anuales innecesarios frente a VVF, si realmente no necesita NSX.
ESXi — Definición técnica de Workload
Per-Core
▼
A nivel técnico (no de licencia), ESXi entiende un workload como cualquier VM en ejecución sobre un host, sin distinción entre tipo de carga. El motor de cómputo asigna recursos de CPU/RAM por VM mediante el scheduler, y características como DRS (Distributed Resource Scheduler) y HA mueven VMs entre hosts para balancear carga o recuperarse de fallas — todo a nivel de "workload = VM individual".
Microsoft Hyper-V
Hyper-V — Incluido en Windows Server
Per-Core
▼
Hyper-V no licencia "workloads" como concepto separado: el hypervisor viene incluido en la licencia de Windows Server (que sí es per-core con mínimo de 8 cores por licencia base). Cada VM que corre dentro no tiene costo de hypervisor adicional — el workload, en este contexto, es simplemente lo que consume recursos del host ya licenciado. Azure Local (ex-Azure Stack HCI) extiende esto agregando una suscripción mensual por nodo gestionado desde Azure, independiente del licenciamiento de Windows Server del guest.
Licencia baseIncluida en Windows Server Datacenter/Standard, per-core con mínimo de 8 cores
Costo adicional VMNinguno por el hypervisor — el costo está en el licenciamiento del guest OS si es Windows
Azure LocalSuscripción Azure adicional por nodo, sobre hardware certificado por Microsoft
Open Source — KVM, Proxmox, XCP-ng
KVM / Proxmox VE / XCP-ng
el destino del éxodo VMware Capacidad
▼
En el mundo open source, el workload (la VM) no tiene costo de licencia por sí mismo — el hypervisor es gratuito. Proxmox VE cobra una suscripción opcional de soporte por socket físico (no por core ni por workload), totalmente desacoplada de cuántas VMs corren en el cluster. Es la razón estructural por la que estas plataformas se volvieron el destino #1 de migración tras el cambio de precios de Broadcom en 2024.
Costo del hypervisor$0 — KVM, Proxmox VE y XCP-ng son gratuitos en su uso core
Modelo de soporte (Proxmox)Suscripción opcional por socket físico, no por core ni por VM
Workloads ilimitadosNo hay límite de VMs ni cobro adicional por escalar el número de workloads
💡 Para una organización con 200 VMs en hosts de 12 cores reales, el ahorro frente al mínimo de 16 cores de Broadcom puede ser la diferencia entre pagar por núcleos que no existen o no pagar nada por el hypervisor.

Backup & Disaster Recovery
5 modelos ▼
Acá el workload SÍ es la unidad de facturación explícita y declarada — pero qué cuenta como "1 workload" varía enormemente entre vendors, y el concepto de air-gap (aislamiento físico o lógico del backup) se construye de forma distinta en cada plataforma.
Veeam
Veeam Universal License (VUL)
el estándar de la industria Per-Workload
▼
Veeam define el workload de la forma más literal de toda la industria: es la unidad exacta de facturación, "portable" entre cualquier producto Veeam y cualquier plataforma de origen (VMware, Hyper-V, Nutanix AHV, AWS, Azure, GCP, físicos, Microsoft 365). Las licencias se venden en packs — Foundation/Advanced/Premium en paquetes de 10 instancias, Essentials en paquetes de 5 — no se puede comprar una cantidad arbitraria como 7.
Cuenta como 1 workload1 VM, 1 servidor físico, 1 base de datos, 1 buzón M365, 1 instancia cloud
EmpaquetadoPacks de 10 instancias (Foundation/Advanced/Premium) o 5 (Essentials)
PortabilidadLa misma licencia VUL cubre on-premises y todas las nubes simultáneamente
Modelo legacyPer-socket discontinuado para ventas nuevas desde el 31/12/2022; conversión obligatoria a VUL al renovar
Sweet spot100-1.000 VMs es el rango donde el modelo escala mejor en costo predecible
📌 La frase repetida por clientes de Veeam es literal: "tenemos workloads en prácticamente cada cloud conocido, y la misma licencia los protege a todos" — esa portabilidad es el argumento de venta central del VUL.
Veeam y el Air-Gap
cómo lo construyen técnicamente Per-Workload
▼
Veeam construye el air-gap como una combinación de tool + repositorio, nunca solo del software de backup: la inmutabilidad real depende de dónde vive el dato protegido, no solo de qué motor lo respaldó. Hay tres caminos típicos en el portfolio Veeam para lograr un aislamiento efectivo del ransomware.
📋 Mecanismos de Air-Gap / Inmutabilidad en Veeam
  • Hardened Repository: Linux con sistema de archivos inmutable a nivel kernel (XFS con atributo immutable), sin acceso root remoto habilitado por defecto
  • S3 Object Lock: cuando el repositorio destino es object storage compatible S3 (AWS S3, Wasabi, MinIO), se aplica retención WORM a nivel de objeto
  • Cloud Vault administrado: storage inmutable y air-gapped en Azure, gestionado completamente por Veeam, con egress y API fees incluidos en el precio por TB
⚠️ Un Hardened Repository mal configurado (con acceso SSH root habilitado, por ejemplo) no es realmente air-gapped aunque el filesystem sea técnicamente inmutable — el aislamiento depende tanto de la configuración como de la tecnología subyacente.
Veeam Community Edition
Capacidad
▼
Versión gratuita con el límite de licencia expresado directamente en workloads: hasta 10 workloads protegidos (VMs, servidores físicos o instancias cloud) sin costo, con las funciones completas de backup y restore. Es la puerta de entrada recomendada para validar Veeam en laboratorio antes de comprar, o para organizaciones realmente pequeñas.
Límite10 workloads (cualquier combinación de VM, físico o cloud)
FuncionesBackup, restore y replicación básica completas — no es una versión recortada en funcionalidad
Otros vendors de Backup
Rubrik / Cohesity
arquitectura inmutable por diseño Capacidad
▼
Rubrik y Cohesity definen el workload de forma similar a Veeam (la unidad protegible), pero su diferencial es arquitectónico: el air-gap es inherente al diseño del sistema de archivos, no una configuración opcional sobre un repositorio Linux genérico. Ningún backup puede ser modificado una vez escrito, sin excepción, ni siquiera por un administrador con credenciales root del sistema de backup.
Air-gapInmutabilidad nativa a nivel de filesystem distribuido, no configuración post-hoc
Diferencial RubrikThreat Hunting + Ransomware Detection + Sensitive Data Discovery integrados
Diferencial CohesityPlataforma secundaria hiperconvergente: backup + DR + archivado + analytics consolidados
Backup Cloud-Native (modelo emergente)
sin contar instancias Consumo
▼
Una nueva camada de soluciones cloud-native (como Eon) está empezando a romper con el modelo "per-workload" por completo: sin infraestructura de backup gestionada por el cliente, sin contar instancias individuales, con precio que escala según storage consumido real en lugar de cuántos workloads protegidos hay. Es una señal de hacia dónde podría moverse el mercado en organizaciones cloud-first puras.
Unidad de facturaciónTB de storage consumido, no cantidad de workloads
FocoBases de datos gestionadas, object storage y Kubernetes — nativo de cloud público
📌 Este modelo todavía no compite con Veeam en el terreno de VMs y servidores físicos tradicionales — su fuerza está en cargas 100% cloud-native.

HCI — Hyperconverged Infrastructure
2 modelos ▼
En HCI el workload vuelve a ser "la VM", pero la licencia se mide por capacidad de cluster — la diferencia clave frente a VMware/Broadcom es que no importa cuántos cores tiene cada CPU individual, sino la capacidad total contratada del cluster.
Nutanix
Nutanix Cloud Infrastructure (NCI)
el destino #1 del éxodo VMware Capacidad
▼
Nutanix licencia capacidad de cluster (cores físicos de CPU totales + SSD), no workloads individuales ni instancias. El workload (la VM) corre libremente dentro de esa capacidad contratada — agregar más VMs no genera costo adicional mientras haya capacidad disponible en el cluster. AHV, el hypervisor propio de Nutanix basado en KVM, viene incluido sin costo adicional dentro de la licencia NCI, a diferencia de VMware donde el hypervisor es el centro del costo.
Unidad de licenciaCores físicos de CPU + capacidad SSD del cluster completo
AHV (hypervisor)Incluido sin costo adicional dentro de NCI — ventaja estructural vs. licenciar ESXi por separado
PortabilidadLicencias por término (1-5 años), portables entre appliances Nutanix, OEM y servidores de terceros
Edición por clusterClusters con licenciamiento mixto bajan automáticamente al tier más bajo presente
Adopción 2026AHV ya supera a ESXi en adopción dentro de la base instalada de clientes Nutanix
💡 La arquitectura de Nutanix incluye el CVM (Controller Virtual Machine) en cada nodo, que gestiona el storage local de forma distribuida — el workload del cliente y el CVM coexisten en el mismo host, pero solo el primero cuenta para el negocio del usuario.
Nutanix Files / Objects (add-ons)
Capacidad
▼
Los servicios de archivos y objetos de Nutanix se licencian también por capacidad (no por workload), pero de forma independiente al NCI base, según corran en modo mixto (mismo cluster que las VMs) o en clusters dedicados exclusivamente a ese servicio.
Nutanix FilesAdd-on para HCI (mixed mode) o licencia dedicada (cluster exclusivo) — ambas por capacidad
Nutanix ObjectsLicencia por capacidad para AOS, en mixed mode o dedicado

📌 Para la conversación con el cliente
Conclusión
▼
Cuando un cliente dice "tenemos 200 workloads", la primera pregunta de un analista de preventa debería ser "¿200 workloads según quién?" — porque esa cifra cambia radicalmente el dimensionamiento y el costo según el contexto:
  • Si son 200 VMs en VMware: hay que contar cores físicos de los hosts, no las VMs, para cotizar Broadcom
  • Si son 200 VMs a migrar a Nutanix: lo que importa es la capacidad total del cluster destino, no la cantidad de VMs
  • Si son 200 workloads a proteger con Veeam: ahí sí la cifra es directamente la base de la cotización — pero hay que verificar si incluye servidores físicos, bases de datos o buzones que se cuentan aparte
  • Si son 200 aplicaciones a migrar a AWS/Azure/GCP: la conversación es de arquitectura (Well-Architected), no de licenciamiento — el costo sale del consumo real proyectado
💡 Este documento es exactamente el tipo de contexto que separa una cotización aproximada de una propuesta técnicamente sólida en preventa cloud.
