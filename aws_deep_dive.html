01 — AWS Well-Architected Framework
6 pilares para diseñar y evaluar arquitecturas cloud seguras, eficientes y resilientes
▼

El AWS Well-Architected Framework es la guía de referencia de Amazon para diseñar y evaluar cargas de trabajo en la nube. No es un set de reglas — es un sistema de preguntas que ayudan a identificar riesgos en la arquitectura antes de que se conviertan en problemas. Está organizado en 6 pilares, cada uno con sus propios principios de diseño y mejores prácticas. Para el consultor cloud de Personal Tech, conocerlo es clave para dos cosas: auditar la arquitectura actual del cliente y diseñar arquitecturas nuevas que el cliente pueda defender ante su directorio.

¿Por qué importa?
Cómo usar Well-Architected en una venta de Personal Tech
El framework como herramienta de preventa, no solo de arquitectura
▼
Para el CTO o arquitecto del cliente
"Lo primero que hacemos antes de proponer cualquier arquitectura es una revisión Well-Architected de lo que tenés hoy. En una reunión de 2 horas identificamos los riesgos más altos de tu arquitectura actual — seguridad, disponibilidad, costo, rendimiento. Ese diagnóstico es gratuito y te queda como activo independientemente de lo que decidas hacer después."
La Well-Architected Tool es gratuita en la consola de AWS. Usarla con el cliente es una forma de agregar valor inmediato antes de cerrar cualquier contrato. El cliente que hizo la revisión con vos, cuando decida migrar, llama a Personal Tech primero.
⚙️
Excelencia Operativa
Ejecutar y monitorear sistemas mejorando continuamente los procesos. Foco en automatización, respuesta a eventos y estándares operativos.
  • Infraestructura como código (IaC): CloudFormation, CDK o Terraform. Nunca cambios manuales en producción.
  • Pequeños cambios frecuentes: deploys pequeños y reversibles son menos riesgosos que grandes releases esporádicos.
  • Anticipar el fallo: diseñar sabiendo que algo va a fallar. Runbooks documentados, alarmas configuradas, respuesta automatizada.
  • Métricas operativas: CloudWatch con dashboards y alertas sobre métricas de negocio, no solo técnicas.
Argumento para el COO
"¿Cuánto tiempo tarda tu equipo IT en desplegar un cambio en producción? ¿Tienen runbooks documentados para los incidentes más frecuentes? El pilar operacional define exactamente cómo Personal Tech gestiona tu infraestructura sin depender de la memoria de una sola persona."
🔐
Seguridad
Proteger información y sistemas. Confidencialidad, integridad de datos, gestión de permisos y detección de eventos de seguridad.
  • Identidad sólida: MFA en todas las cuentas. Roles IAM con mínimos permisos. Nunca credenciales de larga duración en aplicaciones.
  • Trazabilidad completa: CloudTrail activo en todas las regiones. Cada API call queda registrado. Logs centralizados en CloudWatch Logs.
  • Defensa en profundidad: VPC con subredes públicas/privadas, Security Groups, WAF, GuardDuty. Capas de seguridad que se cubren entre sí.
  • Encriptación por defecto: datos en reposo (KMS) y en tránsito (TLS). No como feature opcional — como default.
  • Preparación para incidentes: plan documentado, rol de respuesta definido, simulacros periódicos.
Conexión con Personal Tech: El SOC 24/7 de Personal Tech implementa exactamente este pilar como servicio gestionado. El cliente no tiene que construir la capacidad de detección — la contrata.
🔄
Fiabilidad
Cargas de trabajo que realizan sus funciones previstas y se recuperan rápidamente de los fallos. Diseño de sistemas distribuidos y recuperación ante desastres.
  • Recuperación automática del fallo: CloudWatch Alarms que activan acciones de auto-healing sin intervención humana.
  • Multi-AZ por defecto: ningún componente crítico en una sola zona de disponibilidad. RDS Multi-AZ, ALB, Auto Scaling Groups.
  • RTO y RPO definidos: ¿cuánto tiempo puede estar caído? ¿cuántos datos puede perder? Sin estas definiciones no hay DR real.
  • Gestión de cambios: los cambios en producción son controlados, auditados y reversibles.
Para el COO
"¿Cuál es el RTO de tu aplicación más crítica? ¿Lo probaron? El pilar de fiabilidad de AWS define exactamente cómo diseñamos el DRS de Personal Tech — con un RTO contractual que podés mostrar a tu directorio."
⚡
Eficiencia de Rendimiento
Asignación estructurada de recursos de IT. Selección de tipos y tamaños correctos, monitoreo del rendimiento y eficiencia a medida que evoluciona el negocio.
  • Selección correcta de recursos: elegir el tipo de instancia adecuado para cada workload. Una DB no necesita la misma instancia que un servidor web.
  • Arquitecturas serverless donde aplica: Lambda + API Gateway para cargas intermitentes. Se paga por ejecución, no por tiempo encendido.
  • Cachés en capas: ElastiCache (Redis/Memcached) para DB. CloudFront para contenido estático. Reduce carga y mejora latencia.
  • Auto Scaling: el sistema crece automáticamente con la demanda y se reduce cuando baja. Sin sobredimensionamiento permanente.
💰
Optimización de Costos
Evitar gastos innecesarios. Comprensión del gasto, selección de recursos correctos y escalado sin excesos. Es el pilar de FinOps.
  • Implementar la gestión del gasto en la nube: etiquetado (Tags) de todos los recursos por proyecto, área y entorno.
  • Reserved Instances y Savings Plans: comprometer consumo a 1–3 años para ahorrar hasta 72% vs. on-demand.
  • Instancias Spot: para cargas interrumpibles (batch, rendering, CI/CD) con hasta 90% de descuento.
  • Eliminar recursos zombies: instancias paradas que pagan storage, EIPs no asignadas, snapshots de años.
  • Rightsizing continuo: AWS Compute Optimizer sugiere automáticamente cambios de tipo de instancia.
Conexión con Personal Tech FinOps: El pilar de optimización de costos es exactamente el servicio FinOps de Personal Tech. El cliente que tiene AWS o Azure sin FinOps está desperdiciando entre el 20% y el 35% de su gasto cloud.
🌱
Sostenibilidad
Minimizar el impacto ambiental de las cargas de trabajo en la nube. Modelo de responsabilidad compartida ambiental y maximización de la eficiencia de recursos.
  • Maximizar la utilización: servidores sobredimensionados consumen energía innecesaria. Rightsizing es también sostenibilidad.
  • Usar regiones con energía renovable: AWS publica el mix energético de cada región.
  • Arquitecturas eficientes: serverless consume energía solo cuando ejecuta. Menos recursos inactivos = menos energía.
  • Personal Tech: el DC de Pacheco opera con 100% energía renovable — argumento de sostenibilidad real para empresas con reportes ESG.

02 — Pricing AWS: cómo se cobra y cómo calcular el costo real
Modelos de precio · AWS Pricing Calculator · Egress fees · Cómo construir un TCO honesto
▼

Entender el pricing de AWS es fundamental para dos cosas: diseñar propuestas de Personal Tech que ganen en TCO, y para el servicio de FinOps donde el conocimiento profundo del pricing es lo que genera los ahorros. El pricing de AWS tiene muchas dimensiones ocultas que la mayoría de los clientes no ve hasta que llega la factura.

Los 3 modelos de precio
On-Demand · Reserved Instances · Spot — cuándo usar cada uno y cuánto se ahorra
La base del pricing de EC2 que aplica con variantes a casi todos los servicios
▼
ModeloDescripciónAhorro vs. On-DemandMejor paraRiesgo
On-Demand Pago por hora/segundo de uso. Sin compromiso. Precio de lista. — Cargas impredecibles, picos cortos, testing, entornos no productivos. El más caro para cargas estables. Muchas empresas lo usan para todo sin saberlo.
Reserved Instances (RI) Compromiso de 1 o 3 años a cambio de descuento. Pago por adelantado, parcial o mensual. Hasta 72% Cargas estables y predecibles. Servidores de producción que corren 24/7. Si la carga baja o cambia, la RI queda pagada sin usar. Requiere planificación.
Savings Plans Compromiso de gasto por hora (no de instancia específica). Más flexible que las RI. Hasta 66% Empresas que quieren descuento sin comprometerse a un tipo de instancia específico. Requiere estimación precisa del uso futuro. Sin estimación, el plan queda subutilizado.
Spot Instances Capacidad sobrante de AWS a precio variable, con posibilidad de interrupción con 2 min de aviso. Hasta 90% Batch processing, rendering, CI/CD, análisis de datos, ML training. Cargas tolerantes a interrupciones. AWS puede interrumpir la instancia con 2 minutos de aviso. No usar para producción web.
La estrategia óptima (que Personal Tech FinOps implementa): 60–70% de la carga base en Reserved Instances o Savings Plans + 20–30% en On-Demand para variabilidad + 10–20% en Spot para workloads batch. Este mix puede reducir el gasto total de EC2 entre un 40% y 60% sin cambiar la arquitectura.
Los costos ocultos de AWS
Egress fees · Data transfer · NAT Gateway · Support — lo que no aparece en la demo de AWS
Las sorpresas en la factura que el cliente no vio hasta el mes 2
▼
Costo ocultoQué esCuánto puede representarCómo mitigarlo / argumento Personal Tech
Egress fees (Data Transfer Out) AWS cobra por los datos que SALEN de AWS hacia internet. Entrar datos a AWS es gratis — salir no. Hasta el 20–30% de la factura total en aplicaciones con mucho tráfico de salida. Personal Tech no cobra egress en Personal Cloud. Para salida a AWS, usar Direct Connect que tiene menor costo de egress que internet público.
NAT Gateway Para que instancias en subredes privadas accedan a internet, se usa un NAT Gateway. Cobra por hora Y por GB procesado. En arquitecturas con muchas instancias privadas puede ser $0.05/GB × millones de GBs = sorpresa grande. Revisar si realmente necesitan NAT o si pueden usar VPC Endpoints (más barato) para acceder a servicios AWS.
Soporte AWS El plan Business es el mínimo razonable para producción. Cuesta el 10% de la factura mensual (mínimo $100/mes). Con factura de $10K/mes, el soporte Business agrega $1.000/mes más. Personal Tech incluye soporte en el servicio. Sin costo de soporte adicional por encima del precio del servicio cloud.
Snapshots y backups EBS snapshots se acumulan si no hay política de retención. Se pagan por GB-mes. Empresas con años de snapshots sin gestionar pueden tener $2.000–$5.000/mes en storage de snapshots que nadie usa. FinOps de Personal Tech incluye auditoría de snapshots como primera acción.
Tipo de cambio USD AWS factura en USD. Si el ARS se deprecia, el costo en pesos sube automáticamente sin cambio en el servicio. Una empresa que pagaba $5M ARS/mes puede estar pagando $8M ARS/mes 6 meses después por tipo de cambio, sin consumir más. Personal Cloud factura en pesos. Sin exposición cambiaria. Presupuesto de IT predecible.
Para el CFO que compara AWS vs Personal Tech en precio de lista
"La instancia de AWS parece más barata si mirás solo el precio de la VM. Pero cuando sumás el egress, el NAT Gateway, el soporte Business, el tipo de cambio y el costo de IT para administrarlo, el TCO real es muy diferente. Eso es exactamente lo que hacemos con nuestra calculadora TCO — comparar el costo real, no el precio de lista."

    03 — Arquitecturas de referencia en AWS
    Patrones hexagonales · Microservicios · CQRS · Multi-dominio — con servicios AWS reales
    ▼

    Las arquitecturas hexagonales en AWS (también conocidas como Ports & Adapters) separan la lógica de negocio del núcleo de los detalles técnicos de entrada/salida. El dominio no conoce a AWS — solo conoce interfaces abstractas. Los servicios AWS implementan esas interfaces. Este modelo genera código altamente testeable, portable y resiliente al cambio tecnológico.

    Conceptos clave
    Dominio · Clientes · Adaptadores primarios · Adaptadores secundarios · Puertos
    El vocabulario de la arquitectura hexagonal aplicado a servicios AWS
    ▼
    ConceptoQué esServicios AWS que lo implementan
    DominioLa lógica de negocio pura. No conoce AWS. Solo conoce interfaces (puertos). Es el corazón de la aplicación.No es un servicio AWS — es el código de la aplicación.
    PuertoInterfaz abstracta que define lo que el dominio necesita del mundo exterior (guardar datos, enviar mensajes) o cómo acepta peticiones.Interface/Abstract class en el código.
    ClienteQuién inicia la interacción con el dominio desde el exterior. Dispara la ejecución.API Gateway · SQS · EventBridge · Elastic Load Balancing
    Adaptador primarioRecibe la petición del cliente y llama al dominio. Traduce entre el protocolo externo y el dominio.Lambda · ECS · EKS · EC2
    Adaptador secundarioImplementa los puertos de salida del dominio. Traduce las necesidades del dominio a tecnología concreta.DynamoDB · RDS · Aurora · SQS · SNS · API Gateway (para llamar APIs externas)
    Por qué importa esto para Personal Tech: Un cliente que implementa arquitectura hexagonal puede cambiar de DynamoDB a Personal Cloud Storage, o de Lambda a ECS, sin tocar el dominio. Eso hace que su arquitectura sea agnóstica de proveedor — y Personal Tech puede entrar como adaptador secundario en cualquier parte del sistema.

    Cuándo usar esta arquitectura
    • Microservicio nuevo con pocas operaciones: CRUD básico, consultas simples, webhook handler.
    • Tráfico variable o impredecible: Lambda escala a cero cuando no hay tráfico — costo $0 en horas sin uso.
    • MVP o PoC: entrar en producción rápidamente sin gestionar servidores.
    ✅ Ventajas
    Sin servidores que administrar. Escalado automático a cero. Pago por ejecución. Despliegue en minutos con SAM o Serverless Framework.
    ⚠️ Limitaciones
    Cold starts de Lambda (50–500ms) pueden impactar UX. Timeout máximo de 15 minutos. No sirve para procesos de larga duración.

    Por qué separar lecturas de escrituras
    • Escalado independiente: las lecturas pueden escalar x10 sin afectar las escrituras y viceversa.
    • Escrituras asincrónicas via SQS: el cliente recibe confirmación inmediata y el procesamiento ocurre en background. Mejor UX y mayor resiliencia.
    • Desacoplamiento: si el procesador de escrituras falla, los mensajes quedan en SQS hasta que se recupere — sin pérdida de datos.
    • Optimización de modelos de datos: el modelo de lectura puede estar desnormalizado para performance; el de escritura puede ser normalizado para integridad.

    Cuándo pasar de Lambda a ECS
    • Procesos que duran más de 15 minutos: reportes complejos, procesamiento de archivos grandes, migraciones de datos.
    • Necesidad de base de datos relacional: esquema complejo, joins, transacciones ACID → RDS o Aurora.
    • Llamadas a APIs externas: el dominio necesita consultar sistemas externos (CRM, ERP, pagos). El API Gateway actúa como adaptador secundario.
    • Control total del runtime: ECS con Docker permite usar cualquier lenguaje, versión o dependencia sin las limitaciones de Lambda.
    La regla de cambio de adaptador: Si mañana necesitás cambiar de RDS a DynamoDB (o de Amazon RDS a Personal Cloud DB), el dominio no cambia — solo escribís un nuevo adaptador que implementa el mismo puerto. Eso es exactamente la ventaja de la arquitectura hexagonal.

    Principios del diseño multi-dominio
    • Cada dominio es un microservicio: tiene su propio código, su propio repositorio, su propio ciclo de despliegue.
    • Comunicación via puertos/adaptadores: los dominios no se llaman directamente — usan SQS (asincrónico), EventBridge (eventos) o ALB (HTTP sincrónico).
    • Entornos de cómputo distintos por dominio: el dominio A puede usar Lambda, el B puede usar ECS y el C puede usar EC2 — cada uno elige según sus necesidades.
    • Cambio sin ruptura: si el dominio B cambia de ECS a Lambda, el dominio A no se entera porque la comunicación es via SQS/EventBridge, no por llamada directa.
    Cómo Personal Tech puede entrar en arquitecturas multi-dominio
    "Tu Dominio A puede correr en AWS Lambda y tu Dominio B puede correr en Personal Cloud — ambos comunicados vía SQS. Los datos regulados van al Dominio B en Personal Cloud (dato soberano), los datos no regulados van al Dominio A en AWS. Un solo contrato con Personal Tech gestiona ambos entornos."

    🔴 Huawei Cloud — Alternativa Multi-Cloud

    Huawei Cloud (HEC): Soberanía de datos BCRA, ~20% más barato que AWS, servicios equivalentes.

    Casos de uso: Cumplimiento regulatorio Argentina, presupuesto ajustado, ecosistema Huawei (5G, telecom).

    IBM Cloud: Para empresas legacy (mainframe, Db2, SAP), Watson AI, Red Hat OpenShift hybrid.
