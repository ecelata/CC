⚡ Por qué este documento existe
Cada hyperscaler tiene su propio stack de programas para acompañar una migración: uno para entender madurez organizacional, otro para revisar arquitectura técnica, otro para estimar costos con datos reales, y uno nuevo (con IA agéntica) para ejecutar la migración o modernización en sí. Mezclar estos programas o no saber cuál usar en qué momento es la causa más común de presupuestos mal armados en preventa. Este documento ordena el universo completo: qué hace cada programa, en qué fase del proyecto se usa, y qué entrega como resultado.

Conceptos Base: Las 4 Fases y los 6/7 R's
marco común ▼
Antes de comparar herramientas, hay dos marcos conceptuales que comparten los tres hyperscalers y que conviene tener clarísimos: las fases del ciclo de migración, y las estrategias de disposición (los "R's") que se le asigna a cada workload.
Las 4 Fases del Ciclo de Migración
FASE 1
Assess / Evaluar
Descubrimiento, inventario, TCO, madurez organizacional
FASE 2
Mobilize / Movilizar
Landing zone, gobernanza, capacitación, plan de oleadas
FASE 3
Migrate & Modernize
Ejecución por oleadas, aplicando el R-strategy de cada workload
FASE 4
Operate & Optimize
FinOps, rightsizing continuo, mejora de arquitectura post-migración
Detalle de las 4 fases
Framework
▼
Este patrón de 4 fases (a veces comprimido en 3, fusionando Mobilize dentro de Assess) es prácticamente idéntico entre AWS, Azure y GCP, y es la estructura sobre la que se apoya casi cualquier propuesta comercial de migración seria. Cada fase tiene entregables específicos que la fase siguiente necesita como insumo.
📋 Entregables típicos por fase
  • Assess: inventario de aplicaciones con dueños, mapa de dependencias, TCO a 1 y 3 años, gaps de las 6 dimensiones de madurez (CAF)
  • Mobilize: landing zone desplegada, cuentas/suscripciones/proyectos creados, política de tagging, equipo capacitado, plan de oleadas con dependencias
  • Migrate & Modernize: workloads movidos según su R-strategy asignada, validación funcional, cutover documentado
  • Operate & Optimize: rightsizing continuo, savings plans/reserved instances, gobernanza FinOps, decisiones de modernización adicional
⚠️ El error más común en preventa es saltar directo a cotizar la Fase 3 sin haber hecho un Assess real con datos de utilización — eso genera presupuestos basados en supuestos, no en consumo real, y casi siempre termina sobre-dimensionando recursos.
Las Estrategias de Disposición — Los "R's"
Los 6/7 R's de Migración
común a los 3 hyperscalers Framework
▼
A cada workload identificado en el Assess se le asigna una de estas estrategias. La elección incorrecta de R-strategy es la causa número 1 de sobrecostos post-migración — migrar todo como "Rehost" cuando algunos workloads merecían "Retire" o "Repurchase" es dinero tirado en infraestructura que no debería existir.
1. Rehost"Lift & shift" — mover la VM tal cual, sin cambios de código. El más rápido, el menos optimizado en costo a largo plazo.
2. Replatform"Lift, tinker & shift" — pequeños ajustes para aprovechar servicios gestionados (ej. mover de SQL Server en VM a RDS) sin reescribir la app.
3. Refactor / Re-architectRediseño profundo para arquitectura cloud-native (microservicios, serverless). El más lento y costoso de ejecutar, el más barato de operar después.
4. RepurchaseReemplazar la aplicación legacy por un SaaS equivalente (ej. CRM propio → Salesforce).
5. RetireDar de baja la aplicación porque ya no aporta valor de negocio. Identificarlas reduce el alcance real de la migración.
6. RetainDejarla donde está (por ahora) — aplica a sistemas con dependencias regulatorias, contratos vigentes, o sin caso de negocio claro para migrar todavía.
7. Relocate (la séptima, agregada por AWS)Mover infraestructura VMware completa a VMware Cloud on AWS sin cambios de hypervisor — variante especializada de Rehost.
💡 AWS Transform y AWS OLA, entre otras herramientas, ahora generan automáticamente recomendaciones de R-strategy por aplicación basadas en datos reales de uso, en lugar de depender solo del criterio manual de un arquitecto.
Cloud Adoption Framework vs Well-Architected Framework
CAF vs WAF — La diferencia que se confunde más
Framework
▼
Estos dos frameworks se confunden constantemente porque ambos hyperscalers los publican con nombres similares, pero responden preguntas completamente distintas: el CAF evalúa si la organización está lista (personas, procesos, gobernanza); el WAF evalúa si una arquitectura técnica específica está bien diseñada (seguridad, confiabilidad, costos). Se usan en momentos distintos del proyecto y nunca se reemplazan entre sí.
CAF — Cloud Adoption FrameworkEvalúa madurez organizacional en 6 dimensiones: negocio, personas, gobernanza, plataforma, seguridad y operaciones. Se usa al inicio del proyecto, antes de tocar una sola VM.
WAF — Well-Architected FrameworkEvalúa el diseño técnico de un workload específico ya desplegado o por desplegar, contra pilares como seguridad, confiabilidad y costos. Se aplica de forma rotativa, workload por workload.
📌 En la práctica: el CAF se usa una vez al arrancar el programa de migración (o cuando cambia significativamente el contexto organizacional); el WAF se aplica repetidamente, cada vez que se revisa o diseña una arquitectura puntual.

AWS — El stack completo de migración
7 programas ▼
AWS tiene el ecosistema más maduro y extenso de programas de migración del mercado, con piezas que cubren desde la evaluación de madurez hasta la ejecución asistida por IA agéntica. Ordenado según el momento del proyecto en que se usa cada uno.
Madurez y Arquitectura
AWS Cloud Adoption Framework (CAF)
Madurez
▼
Framework de madurez organizacional de AWS, usado para identificar gaps de capacidad antes de iniciar la migración técnica. Es el primer paso recomendado por AWS para construir el modelo de TCO y entender qué tan preparada está la organización, no solo la infraestructura.
Dimensiones evaluadasNegocio, Personas, Gobernanza, Plataforma, Operaciones, Seguridad
Cuándo se usaAl inicio del programa, en paralelo o antes del Assess técnico
ResultadoMapa de gaps de capacidad por dimensión, insumo para el plan de Mobilize
AWS Well-Architected Framework (WAF)
Arquitectura
▼
El framework de revisión arquitectónica más detallado y tool-driven de los tres hyperscalers, con una biblioteca extensa de "Lenses" especializados por tipo de carga (Machine Learning, IoT, SaaS, Serverless). Se aplica workload por workload, nunca al ambiente completo de una vez.
PilaresExcelencia Operacional, Seguridad, Confiabilidad, Eficiencia de Rendimiento, Optimización de Costos, Sostenibilidad
HerramientaAWS Well-Architected Tool — gratuita, en la consola
DiferencialLenses especializados por industria/tecnología — la mayor profundidad técnica del mercado
💡 Se usa tanto antes de migrar (validar el diseño objetivo) como después (revisión periódica de lo ya desplegado) — no es exclusivo de la fase de migración.
Descubrimiento y TCO (Assess)
AWS Application Discovery Service
la fuente de datos TCO
▼
Herramienta de descubrimiento que recolecta datos de configuración, utilización y dependencias de los servidores on-premise. Es el insumo de datos que alimenta tanto a Migration Evaluator como a AWS Transform — sin un buen discovery, cualquier estimación posterior es una suposición.
ModosAgentless (vía vCenter/Hyper-V) o Agent-based (instalado en cada servidor)
Datos recolectadosCPU, RAM, storage, red, procesos en ejecución y dependencias entre servidores
CostoSin costo — incluido como parte del proceso de Assess
AWS Migration Evaluator
ex-TSO Logic TCO
▼
Servicio gratuito de evaluación de TCO basado en datos reales de utilización (no en supuestos). Genera un Quick Insights de una sola página en 48 horas tras instalar el collector, y un reporte completo de business case con comparación a 1 y 3 años entre el costo on-premise actual y el costo proyectado en AWS, incluyendo análisis de licencias (BYOL vs. License Included).
Tiempo a primer resultadoQuick Insights en 48 horas tras instalar el collector agentless
TCO cubierto on-premiseServidores, storage, software/licencias/soporte, facilities (rack, energía, real estate)
TCO cubierto AWSEC2, Reserved Instances, storage, bases de datos, VMware Cloud on AWS, licencias
CostoSin costo — servicio gratuito de AWS
Ideal paraEnterprises con infraestructura compleja que necesitan un business case formal y defendible
📌 Migration Evaluator es el predecesor conceptual y complementario de AWS Transform: Evaluator se enfoca 100% en el business case de TCO; Transform además ejecuta la migración con IA agéntica.
AWS Optimization and Licensing Assessment (OLA)
foco en licenciamiento TCO
▼
Programa gratuito enfocado específicamente en optimización de licenciamiento de software de terceros (Windows Server, SQL Server, Oracle, IBM DB2, RHEL) al migrar a AWS. Analiza uso real de recursos y dependencias de aplicación para modelar opciones de despliegue, recomendando el mix óptimo entre on-demand, spot, BYOL y savings plans.
Ahorro promedio Windows Server77% de reducción en costos de licencia (dato de AWS)
Ahorro promedio SQL Server45% de reducción, vía consolidación, rightsizing de cores y optimización de edición
Quién lo lideraTípicamente el CIO/CTO como Migration Sponsor, con Solution Architects, DBAs, ITAM y Procurement
EntregablesExecutive Summary, Licensing Summary, Dedicated Host Mapping, SQL Optimization, estimación de costos optimizada
Caso real (Damart)56% de reducción en licencias Oracle + 50% de reducción en infraestructura AWS
💡 OLA y Migration Evaluator no son excluyentes: Evaluator da el TCO general de infraestructura, OLA profundiza específicamente en la capa de licenciamiento de software — en proyectos con SQL Server u Oracle pesados, conviene corren ambos.
Ejecución y Modernización (Migrate)
AWS Transform
IA agéntica — el más nuevo de todos Ejecución
▼
El primer servicio de IA agéntica de AWS para migración y modernización a gran escala. No es solo una herramienta de estimación: ejecuta activamente el análisis, planificación, documentación y transformación de aplicaciones Windows .NET, mainframes (COBOL/JCL) y entornos VMware completos, con agentes especializados que colaboran en un workspace compartido con el equipo humano.
Velocidad declaradaHasta 5x más rápido que modernización manual; casos de hasta 1.5M líneas de código analizadas por mes
MainframeExtrae lógica de negocio de COBOL/JCL, genera microservicios, con integración nativa a Kiro para especificación y generación de código
VMware → AWSDescubre el entorno on-premise, prioriza apps por negocio, mapea dependencias, migra Windows/Linux x86, hypervisors (VMware, Hyper-V, Nutanix, KVM) y bare-metal
TCO integradoGenera business case de TCO en minutos a partir de exports de RVTools, Migration Evaluator agentless collector o formato MPA (ModelizeIT/Cloudamize)
Modo de trabajoHuman-in-the-loop obligatorio — el código y las especificaciones generadas por IA se validan siempre por expertos humanos
Caso real (aerolínea)80% de reducción en tiempo y costo estimado en modernización de miles de funciones Lambda
⚠️ AWS Transform es una herramienta de ejecución asistida, no un sustituto del juicio de un arquitecto senior — el "human in the loop" no es opcional en mainframe ni en transformaciones de lógica de negocio crítica.
AWS Migration Hub
Ejecución
▼
Panel central gratuito que orquesta y centraliza el seguimiento del progreso de todas las migraciones, integrando datos de Application Discovery Service y de las herramientas de migración (MGN, DMS) en una sola vista. No estima costos — coordina y trackea ejecución.
Función principalVisibilidad centralizada del progreso de migración across múltiples herramientas y cuentas
CostoSin costo — se paga solo por los recursos AWS subyacentes consumidos
Funding y Aceleración
AWS Migration Acceleration Program (MAP)
la billetera del programa Funding
▼
El programa estructurado de financiamiento de AWS para migraciones, ejecutado siempre a través de un AWS Partner con competencia de Migración. No es una herramienta técnica — es el mecanismo que convierte el trabajo de Assess, Mobilize y Migrate en créditos reales que reducen el costo del proyecto. Tuvo un cambio mayor en julio 2024 que amplió significativamente su alcance.
FasesAssess → Mobilize (~20% de ARR proyectado) → Migrate & Modernize (15-25% de ARR, mayor para SAP/mainframe/VMware)
Funding máximo (post jul. 2024)Hasta $2.000.000 USD en funding de partner, antes el tope era $460.000
MAP Lite (entrada mid-market)Disponible desde $100.000 USD de ARR (antes el mínimo era $250.000) — 15% de ARR en fases tempranas + 10% adicional en migración
Requisito claveTagging correcto de los recursos migrados es obligatorio para que el spend cuente como elegible para créditos
Cómo se accedeExclusivamente a través de un AWS Partner con AWS Migration Competency (200+ partners certificados globalmente)
Forma del fundingCréditos de servicios AWS otorgados al Partner, no efectivo directo al cliente final
💡 El funding de MAP se paga contra hitos documentados y consumo real, no contra un contrato firmado — cada fase requiere entregables aprobados por AWS antes de liberar el siguiente tramo.

Microsoft Azure
3 programas ▼
El stack de Azure es más compacto que el de AWS, con fuerte foco en entornos Microsoft-céntricos (Windows Server, SQL Server, .NET) y en escenarios híbridos.
Framework y Arquitectura
Azure Well-Architected Framework
Arquitectura
▼
Explícitamente workload-centric: se aplica a una aplicación o plataforma específica, nunca al tenant completo de la organización. Restructurado en 2023 de 6 a 5 pilares, absorbiendo sostenibilidad dentro de los pilares existentes en lugar de tratarla como categoría separada.
PilaresConfiabilidad, Seguridad, Optimización de Costos, Excelencia Operacional, Eficiencia de Rendimiento
DiferencialFuerte en gobernanza y soporte de escenarios híbridos (Azure Arc, Azure Local)
Descubrimiento y TCO
Azure Migrate
el equivalente a Migration Evaluator + Discovery TCO
▼
Hub centralizado de Microsoft que combina descubrimiento, assessment y migración en una sola plataforma. Usa discovery agentless para inventariar VMware, Hyper-V y servidores físicos sin instalar software en cada guest, y genera automáticamente business cases de TCO con métricas de sostenibilidad incluidas — algo que ni AWS ni GCP destacan tanto en sus reportes.
DiscoveryAgentless — sin instalación en servidores individuales, vía vCenter/Hyper-V/físicos
Fortaleza distintivaEntornos Windows Server y SQL Server — el estándar de facto para migrar a Azure
Apps soportadasDiscovery y assessment de apps .NET y Java, con recomendaciones de rightsizing basadas en historial de performance
CostosDiscovery y assessment gratuitos; migración de servidor gratis los primeros 180 días por máquina, luego cargo modesto por instancia; BD y apps web migran gratis siempre
Limitación reconocidaOptimizado para stack Microsoft — menor profundidad en entornos heavy-Linux o con bases de datos no-Microsoft
📌 Azure Migrate tiene un ecosistema rico de herramientas de terceros integradas (Cloudamize fue una de las primeras, desde 2019), aunque su escalabilidad nativa es más cómoda en rangos de 5-50 VMs que en migraciones masivas de 1000+.
Azure Hybrid Benefit
Funding
▼
El equivalente Azure a la lógica BYOL de AWS OLA: permite reutilizar licencias on-premise de Windows Server y SQL Server con Software Assurance (o suscripciones equivalentes) directamente en Azure, evitando pagar el costo de licencia incluida sobre el cómputo.
Aplica aWindows Server y SQL Server con Software Assurance vigente
BeneficioReducción directa del costo de cómputo al no pagar licencia incluida sobre el VM/instancia

Google Cloud Platform
2 programas ▼
El stack más chico de los tres en cantidad de programas formales, con sesgo natural hacia cargas de datos y Machine Learning — coherente con el origen de Google como compañía de datos.
Descubrimiento y TCO
Google Cloud Migration Center
ex-"Migrate for Compute Engine" TCO
▼
Herramienta unificada de Google para descubrimiento, planificación de migración y estimación de costos, con foco declarado en velocidad y mínimo downtime. Automatiza el proceso de planificación de forma similar a Azure Migrate, pero con integración nativa hacia BigQuery y Vertex AI para cargas que terminan en analítica o ML.
Función principalDiscovery, assessment de costos y planificación de migración de VMs a Compute Engine
Fortaleza distintivaWorkloads de datos y ML — integración natural con BigQuery, Vertex AI, Dataflow
Modelo de costos GCPEgress reducido significativamente en 2025-2026 frente a AWS/Azure — relevante para cargas con alta transferencia saliente
💡 Para organizaciones con foco en datos y analítica más que en cómputo tradicional, GCP Migration Center suele requerir menos trabajo adicional de modernización post-migración, porque el destino natural ya es BigQuery/Vertex AI.

Huawei Cloud
3 programas ▼
El cuarto hyperscaler relevante en LATAM (incluyendo Argentina, vía Personal Tech). Tiene un framework propio de adopción con assessments de madurez, y una herramienta de migración (Migration Center) con una particularidad única: puede leer directamente el billing de AWS para construir el TCO comparativo.
Framework de Madurez
Huawei Cloud Adoption Framework (CAF)
Madurez
▼
Framework propio de Huawei, estructurado de forma similar al de AWS/Azure pero con 7 maturity assessments específicos ejecutados directamente desde la consola de Migration Center: DevOps, Landing Zone, Seguridad, Big Data, Base de Datos, Modernización de Aplicaciones y Cloud-Native. Cada assessment es un cuestionario guiado que termina en un reporte exportable en PDF con sugerencias de mejora.
Los 7 assessmentsDevOps · Landing Zone · Seguridad · Big Data · Base de Datos · Modernización de Apps · Cloud-Native
FormatoCuestionario por rol (las preguntas cambian según el perfil de quien responde)
ResultadoReporte de madurez con sugerencias de mejora y acceso a servicios profesionales relacionados
📌 A diferencia de AWS y Azure, Huawei integra estos assessments de madurez directamente dentro de la misma consola de Migration Center — no son un programa separado con su propia herramienta.
Discovery, TCO y Ejecución
Migration Center (MgC)
discovery + TCO + ejecución, todo en uno TCO
▼
La plataforma central de migración de Huawei Cloud, equivalente conceptual a Azure Migrate o GCP Migration Center. Su rasgo más distintivo: el módulo de TCO Analysis para migración cross-cloud permite compartir credenciales de solo lectura de la cuenta AWS del cliente, y MgC analiza directamente el billing real para identificar qué recursos se están usando y mapearlos a sus equivalentes en Huawei Cloud — sin necesidad de exportar manualmente el inventario.
TCO cross-cloudLee billing real de AWS vía credenciales compartidas; actualmente soporta AWS como origen para el análisis automatizado
Mapeo de serviciosEmpareja automáticamente recursos del cloud origen (ej. EC2, RDS) con sus equivalentes en Huawei Cloud (ECS, RDS)
Servicios destacados monitoreadosECS (cómputo), EIP, RDS for MySQL, EVS (storage en bloque), MRS (MapReduce/Big Data)
Maturity AssessmentsLos 7 assessments del CAF de Huawei se ejecutan desde esta misma consola
💡 Para un cliente que ya está en AWS y evalúa Huawei Cloud como alternativa (relevante en Argentina por el contexto de precios en pesos y datacenter local), este análisis de billing real es más persuasivo en una propuesta que un comparativo de lista de precios genérico.
Suite de Ejecución: SMS, DRS, OMS, CDM
Ejecución
▼
A diferencia de AWS (que concentra ejecución en Transform + MGN + DMS) o Azure (todo dentro de Azure Migrate), Huawei separa la ejecución en 4 servicios especializados según el tipo de dato a mover, cada uno con su propia herramienta dedicada.
📋 Las 4 herramientas de ejecución
  • SMS (Server Migration Service): replicación a nivel de bloque de VMs Windows/Linux hacia ECS o Flexus, equivalente a AWS MGN
  • DRS (Data Replication Service): migración online de bases de datos (MySQL, PostgreSQL, SQL Server, Oracle, MongoDB) con downtime mínimo, equivalente a AWS DMS
  • OMS (Object Storage Migration): transferencia masiva hacia OBS desde S3, NAS on-premise u otros object stores
  • CDM (Cloud Data Migration): migración especializada para data lakes y data warehouses
Huawei Cloud EulerOS (HCE)
migración a nivel de sistema operativo Arquitectura
▼
Capa adicional que no tiene un equivalente directo tan formalizado en AWS/Azure/GCP: una herramienta dedicada (x2hce) para migrar el propio sistema operativo de instancias existentes (CentOS, EulerOS de versiones anteriores) hacia HCE, el Linux empresarial propio de Huawei, sin necesidad de recrear la instancia desde cero.
OS soportados como origenCentOS 8, EulerOS 2.9 / 2.10
Qué se preservaIP, dirección MAC y el disco de datos permanecen sin cambios durante la migración de OS
RelevanciaEspecialmente útil dado el fin de soporte de CentOS — ofrece una ruta de migración de OS sin re-provisionar la VM completa
⚠️ El tipo de disco del sistema no puede cambiarse después de la migración de OS, y el cambio de BIOS a UEFI no está soportado — son restricciones a verificar antes de comprometerse con esta ruta en una propuesta.

Herramientas Multi-Cloud / Vendor-Neutral
3 herramientas ▼
Cuando el cliente todavía no decidió a qué cloud va, o cuando el destino es explícitamente híbrido/multi-cloud, estas herramientas alimentan de datos a cualquiera de los tres hyperscalers por igual.
Discovery y TCO Vendor-Neutral
RVTools
el formato de exportación estándar TCO
▼
Herramienta gratuita y muy difundida que extrae inventario detallado de un entorno VMware vCenter (VMs, hosts, datastores, redes, snapshots). Su export en Excel se volvió un formato cuasi-estándar de la industria: tanto AWS Transform como otras herramientas de assessment aceptan directamente archivos RVTools como insumo de discovery.
CostoGratuito
AlcanceExclusivamente entornos VMware vCenter
Uso típicoPrimer paso rápido de inventario antes de instalar herramientas de discovery más pesadas
Cloudamize
TCO
▼
Plataforma de analítica de alta precisión para planificación de migración. Calcula requerimientos de cómputo, storage y red, generando comparaciones de TCO detalladas simultáneas entre AWS, Azure y GCP — útil específicamente cuando el cliente todavía está decidiendo el proveedor destino.
DiferencialComparación de TCO multi-cloud en un solo reporte, sin sesgo hacia un hyperscaler
IntegraciónFue una de las primeras herramientas de terceros integradas al ecosistema de Azure Migrate (desde 2019)
Movilidad Híbrida VMware
VMware HCX
clave para escenarios híbridos VMware Ejecución
▼
Herramienta de movilidad de aplicaciones e hibridez de infraestructura de VMware. Es la pieza clave cuando el destino es VMware Cloud on AWS, Azure VMware Solution o Google Cloud VMware Engine — permite migrar VMs en vivo entre el datacenter on-premise y cualquiera de esos tres destinos sin cambiar de hypervisor ni reconfigurar IPs.
Función de assessmentEvalúa compatibilidad de workloads para el movimiento hacia los tres destinos VMware-en-cloud mencionados
Ventaja claveMigración en caliente sin re-IP, manteniendo el mismo hypervisor — reduce drásticamente el riesgo de migración
Contexto post-BroadcomRelevante para organizaciones que migran a cloud para escapar del nuevo modelo de licenciamiento per-core sin perder su inversión en VMware
📌 Esta es la herramienta puente para clientes con alta inversión en VMware que quieren ir a cloud público sin reconstruir toda su infraestructura desde cero.

Conclusión
▼
Cuando un cliente pide "una cotización de migración a AWS/Azure/GCP" sin más contexto, el orden recomendado para que el número final sea defendible es:
  • 1. Evaluar madurez organizacional (CAF) — identifica si faltan capacidades antes de tocar infraestructura
  • 2. Descubrimiento real de datos (Discovery / Migration Evaluator / Azure Migrate / Migration Center) — nunca estimar sobre supuestos
  • 3. Asignar R-strategy por workload — no todo es Rehost, y mezclar mal las estrategias infla el costo
  • 4. Si hay licenciamiento de terceros pesado (Windows, SQL, Oracle), correr OLA o Azure Hybrid Benefit en paralelo
  • 5. Validar el diseño técnico final contra el Well-Architected Framework correspondiente
  • 6. Recién ahí, calcular si aplica funding (MAP u otros) para reducir el costo neto al cliente
💡 Saltar el paso 2 (discovery real) es el error más frecuente en preventa — cotizar "a ojo" sobre lo que el cliente cree que tiene, en lugar de lo que realmente está usando, es la principal causa de presupuestos que después no cierran en la ejecución.
