01
Aplicación Web 3 Capas — Alta Disponibilidad
El más usado en enterprise
Servicios involucrados
Detalle de cada componente y su rol en la arquitectura
▼
Route 53
DNS con health checks. Failover automático entre AZs. Enruta el tráfico al ALB más cercano o al secundario si el primario falla.
CloudFront + WAF
CDN global que cachea contenido estático. WAF integrado bloquea OWASP Top 10, DDoS y ataques de bots antes de llegar al origen.
ALB (Application Load Balancer)
Distribuye tráfico HTTP/HTTPS entre instancias EC2 según health checks. Soporta routing por path (/api → microservicio, / → frontend).
EC2 Auto Scaling Group
Grupo de instancias que escala automáticamente según CPU, requests o métricas custom. Min 2 instancias en 2 AZs para alta disponibilidad.
RDS Multi-AZ
Base de datos relacional con réplica sincrónica en otra AZ. Failover automático en <60 segundos si la instancia primaria falla.
ElastiCache (Redis)
Cache en memoria para sesiones de usuario y datos frecuentes. Reduce la carga en RDS hasta un 80% para lecturas repetitivas.
S3
Assets estáticos (imágenes, CSS, JS), backups de RDS, logs de acceso. Integrado con CloudFront para distribución global.
Flujo de una request
1
Usuario resuelve DNS en Route 53 → obtiene el IP del CloudFront distribution.
2
CloudFront responde con el contenido cacheado (CSS, JS, imágenes) sin llegar al origen. WAF filtra ataques.
3
Requests dinámicas (/api) pasan al ALB en la subnet pública. El ALB elige la instancia EC2 más sana.
4
La instancia EC2 consulta ElastiCache primero (cache hit = sin ir a RDS). Cache miss: consulta RDS Primary.
5
RDS escribe sincrónicamente en el Standby de la AZ2. Si Primary falla, el Standby se promueve automáticamente.
Personal Tech: Esta arquitectura puede replicarse en la nube privada de Pacheco usando VMs + HAProxy/NGinx como ALB + MySQL Multi-AZ. El cliente obtiene la misma resiliencia con dato soberano en Argentina.
02
API Serverless — Costo cero cuando no hay tráfico
Startups · Microservicios · Eventos
Servicios y flujo
Cuándo elegir serverless — ventajas y limitaciones
▼
API Gateway
Punto de entrada único para todas las APIs. Maneja autenticación, throttling (límite de requests por segundo), SSL, transformación de requests/responses y CORS.
Lambda
Función de código que se ejecuta en respuesta a eventos. Sin servidor que gestionar. Escala de 0 a miles de ejecuciones simultáneas en segundos. Tiempo máximo: 15 minutos.
DynamoDB
NoSQL serverless de latencia milisegundo garantizado. Escala automáticamente. Ideal para serverless porque no tiene conexiones persistentes como RDS.
Cognito
Autenticación y autorización serverless. Gestiona usuarios, tokens JWT, MFA y federación con Google/Microsoft/redes sociales sin código de autenticación propio.
SQS
Cola de mensajes para desacoplar servicios. La Lambda de eventos procesa mensajes de forma asíncrona. Si falla, el mensaje vuelve a la cola automáticamente (retry).
Cuándo NO usar serverless: Funciones que corren continuamente (websockets persistentes), alto volumen de requests constante (las Reserved Instances serían más baratas), dependencias de librerías muy pesadas (>250MB) o que requieren estado compartido entre ejecuciones.
03
Data Lake & Analytics — Procesar petabytes sin infraestructura
Analytics · BI · Data Science
Detalle de servicios
Las 4 zonas del Data Lake y cuándo usar Athena vs. Redshift
▼
Kinesis Data Firehose
Ingestión en tiempo real de streams de datos (IoT, logs, clicks) directamente a S3, Redshift o Elasticsearch. Serverless, escala automáticamente.
S3 (Data Lake)
El lago de datos central. Organizado en zonas: raw (datos crudos sin procesar), processed (limpios), curated (listos para análisis), archive (Glacier para datos históricos).
AWS Glue
ETL serverless basado en Spark. Crawlers que descubren el esquema automáticamente. Transforma datos de /raw a /processed. Data Catalog: el catálogo de metadatos del lake.
Athena
SQL sobre S3 sin servidor. Pago por query ($5/TB procesado). Ideal para análisis ad-hoc y equipos de Data Science. No requiere aprovisionar infraestructura.
Redshift
Data Warehouse para queries SQL complejos sobre petabytes. Mejor para reportes predefinidos y alto volumen de usuarios de BI. Serverless disponible desde 2022.
QuickSight
BI serverless nativo AWS. Dashboards interactivos conectados a Athena, Redshift, S3, RDS. SPICE: motor de cálculo en memoria para respuestas instantáneas.
Athena vs. Redshift: Athena si el equipo hace consultas ad-hoc esporádicas y el volumen varía mucho ($0 cuando no se usa). Redshift si hay un equipo grande de analistas con consultas predefinidas y recurrentes sobre mismos datasets (mejor precio a alto uso continuo).
04
Microservicios con Kubernetes (EKS)
Aplicaciones complejas · DevOps maduro
Conceptos K8s clave
Pods, namespaces, Ingress, node groups — la terminología que hay que manejar
▼
Pod
Unidad mínima de K8s. Uno o más contenedores que comparten red y storage. Si un pod falla, K8s crea uno nuevo automáticamente en el nodo más disponible.
Namespace
Partición lógica del cluster. Permite tener múltiples entornos (frontend, api, workers) o equipos aislados en el mismo cluster físico, con sus propias políticas de recursos.
ALB Ingress Controller
Integración nativa AWS. Crea automáticamente un Application Load Balancer en AWS por cada Ingress definido en K8s. Sin configuración manual del ALB.
ECR
Elastic Container Registry. Repositorio privado de imágenes Docker integrado con IAM. Los nodos de EKS pullan imágenes de ECR sin credenciales adicionales.
Fargate Spot
Serverless containers con descuento de hasta 70%. Para workers y batch jobs tolerantes a interrupciones. Sin gestión de nodos EC2 en ese namespace.
05
Hybrid Cloud — On-Premise conectado a AWS
Enterprise · BCRA · Dato soberano
Servicios de conectividad híbrida
Direct Connect vs. VPN · Transit Gateway · AD Connector — las piezas del híbrido
▼
AWS Direct Connect
Circuito dedicado de 1–100 Gbps entre el datacenter y AWS. Latencia predecible, sin variabilidad de internet. Personal Tech es partner certificado — provisiona el circuito desde Argentina.
VPN Site-to-Site (backup)
Túnel IPSec sobre internet como backup del Direct Connect. Si el circuito falla, el tráfico conmuta automáticamente a la VPN. Mayor latencia pero garantiza continuidad.
Transit Gateway
Hub central que conecta múltiples VPCs, Direct Connect y VPN en una sola entidad gestionada. Sin Transit Gateway, cada VPC necesita peering individual con cada otra — exponencialmente complejo.
AD Connector
Proxy que redirige las solicitudes de directorio de AWS al Active Directory on-premise. Los usuarios usan las mismas credenciales corporativas para acceder a recursos en AWS.
Caso Personal Tech: Personal Tech puede ser el proveedor del circuito Direct Connect, el cloud privado soberano (Pacheco) y la conectividad a AWS — todo en un solo contrato. El cliente no necesita hablar con AWS, con la telco y con un ISP por separado.
06
Disaster Recovery — Estrategias por RTO/RPO
BCRA · Continuidad del negocio · SLA
Servicios clave de DR
AWS Backup · Aurora Global · Route 53 failover · S3 Cross-Region Replication
▼
AWS Backup
Servicio centralizado para gestionar backups de EC2, RDS, EFS, DynamoDB y más. Políticas de retención, cifrado automático y copias cross-region en un solo lugar.
Aurora Global Database
Replicación física de Aurora entre regiones con RPO <1 segundo y RTO <1 minuto. La región secundaria puede promovida a primaria en caso de desastre.
Route 53 Health Checks
Monitorea la salud del endpoint primario y redirige automáticamente el DNS a la región DR si el primario falla. Tiempo de failover: 60–120 segundos (TTL del DNS).
S3 Cross-Region Replication
Replica automáticamente cada objeto subido a S3 en otra región. Asegura que los backups y assets estén disponibles aunque una región entera caiga.
Para clientes regulados (BCRA): La normativa exige RTO y RPO documentados con prueba semestral. Personal Tech puede proveer el sitio DR (Hornos como secundario de Pacheco) + documentación para la auditoría. Sin necesidad de que el cliente construya su propio site DR.
07
Pipeline de Machine Learning — De datos crudos a modelo en producción
IA Generativa · MLOps · SageMaker
El ciclo MLOps completo
Del dato crudo al modelo en producción — y el loop de reentrenamiento
▼
1
Datos: Datos crudos de múltiples fuentes en S3. Glue los limpia, normaliza y lleva a /training. El Feature Store guarda features reutilizables entre proyectos.
2
Entrenamiento: SageMaker Training Jobs ejecutan el entrenamiento en instancias GPU (ml.p4d.24xlarge = 8×A100). Los experimentos se registran en MLflow o en el propio Experiments de SageMaker.
3
Evaluación: El modelo se evalúa automáticamente con métricas definidas (accuracy, F1, AUC). Si no supera el umbral mínimo, el pipeline no lo promueve a producción.
4
Deploy: El modelo aprobado se despliega como Endpoint de SageMaker (inferencia en tiempo real) o como Batch Transform (inferencia masiva). API Gateway + Lambda hacen de proxy para la app.
5
Monitor + Retrain: Model Monitor detecta data drift (los datos reales en producción empiezan a diferir del training set). Cuando supera el umbral, dispara automáticamente un nuevo ciclo de entrenamiento.
IA Generativa: Para casos con LLMs (Bedrock/Claude/GPT-4), no es necesario entrenar desde cero. El pipeline simplifica a: datos del cliente → fine-tuning o RAG → endpoint del modelo → app. SageMaker JumpStart tiene 300+ modelos listos para hacer fine-tuning con un click.
