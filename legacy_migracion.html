01 — ¿Qué es un sistema legacy? La definición honesta
Más allá de "viejo" — los criterios reales que definen un sistema como legacy
▼

Un sistema legacy no es simplemente un sistema viejo — es cualquier sistema que ya no puede evolucionar al ritmo que el negocio lo necesita, independientemente de su edad. Un sistema de 30 años puede no ser legacy si se mantiene activo. Un sistema de 5 años puede serlo si fue construido con tecnología ya obsoleta. La antigüedad es un síntoma, no la causa.

Definición técnica
Los 6 criterios que definen un sistema como legacy
Si cumple 3 o más → es legacy
▼
  • Tecnología sin soporte activo: el fabricante dejó de publicar parches de seguridad. Windows Server 2012, Java 8, COBOL sin comunidad activa.
  • Desarrolladores escasos o únicos: hay 1–2 personas en el mundo que entienden el código. Si renuncian, el sistema es intocable.
  • No tiene API ni integración moderna: no puede conectarse a otros sistemas sin desarrollos a medida costosos y frágiles.
  • Escalado manual e inflexible: para agregar capacidad hay que comprar hardware, esperar entrega, instalar físicamente.
  • Documentación inexistente o desactualizada: nadie sabe exactamente qué hace cada parte del sistema.
  • No soporta las expectativas modernas del usuario: sin mobile, sin tiempo real, sin self-service, sin analítica incorporada.
La analogía del auto sin GPS: Un auto de 2005 funciona perfectamente para moverse de A a B. Pero no tiene GPS integrado, no se conecta al celular, no tiene asistente de mantenimiento y si necesita repuestos específicos hay que buscarlos en desarmaderos. Técnicamente anda. Estratégicamente, está tres generaciones atrás. Eso es un sistema legacy.

02 — El lastre: sistemas que frenan y deben migrar por necesidad
Cuando mantener es más riesgoso que migrar — el punto de no retorno
▼

Hay sistemas legacy que ya no son una opción de mantener — son una obligación de migrar. No por oportunidad estratégica sino por riesgo operativo, regulatorio o de seguridad. La pregunta no es "¿deberíamos migrar?" sino "¿cuánto tiempo más podemos soportar el costo del riesgo?"

Los 5 síntomas del sistema que ya no da para más
Señales de alerta que indican que la migración es urgente, no opcional
▼
🔓
Vulnerabilidades sin parche
El fabricante ya no publica actualizaciones de seguridad. Las CVEs (vulnerabilidades conocidas) se acumulan sin solución. Es cuestión de tiempo hasta el incidente. Windows Server 2012 tiene decenas de vulnerabilidades críticas sin parche desde octubre 2023.
👴
El "guardián del código" se está yendo
Hay una sola persona que entiende el sistema. Está cerca de jubilarse o renunciar. Cuando se va, el sistema se vuelve intocable. Cualquier bug o cambio requerido puede ser un desastre operativo.
📋
Incumplimiento regulatorio inminente
SAP R/3 pierde soporte oficial en 2027. El deadline del fabricante hace que la migración sea obligatoria — la empresa no puede elegir cuándo, solo cómo.
💸
Costo de mantenimiento desproporcionado
El sistema requiere consultores especializados carísimos para cualquier cambio. Cada modificación es una operación de cirugía mayor que cuesta 10× lo que debería.
🔌
Hardware sin repuestos
El servidor que lo corre tiene 15 años y ya no tiene soporte. Si falla un componente, el sistema se cae y no hay forma de reemplazarlo rápidamente.
🐌
Incapacidad de adaptarse al negocio
El negocio quiere agregar una función nueva y el sistema tarda 12 meses y $200K en implementarla. La competencia lo hace en 2 semanas con SaaS moderno.
🚨 El costo real de no migrar: Gartner estima que por cada año que se posterga la migración de un sistema legacy crítico, el costo de la eventual migración aumenta entre 15 y 25%. El "ahorro" de no migrar hoy es una deuda que se paga con intereses.
La "deuda técnica" — el concepto que explica todo
Por qué los sistemas legacy son literalmente una deuda financiera con intereses
▼
La analogía de la deuda financiera: La deuda técnica es exactamente igual a una deuda financiera. Cuando se toma un atajo en el desarrollo ("lo hacemos rápido y después lo mejoramos"), se toma prestado tiempo futuro. Como toda deuda, tiene interés: cada mes que no se paga, el mantenimiento es más difícil, más caro y más riesgoso. Ignorarla no la elimina — la multiplica.
Los 3 tipos de deuda técnica en sistemas legacy
⚡
Deuda deliberada
"Lo hacemos rápido para el lanzamiento y lo mejoramos después." El "después" nunca llega y el código se acumula sin revisión.
⏳
Deuda por obsolescencia
El sistema era bueno cuando se construyó. Pero el mundo cambió y el sistema no. No es culpa de nadie — es la ley del tiempo.
🎲
Deuda accidental
Malas prácticas que nadie detectó en el momento. Código duplicado, sin tests, sin documentación. Visible solo cuando algo falla.

03 — Sistemas que funcionan bien pero no aprovechan lo nuevo
La segunda razón para migrar: no la obligación sino la oportunidad competitiva perdida
▼

Este es el caso más difícil de vender internamente: el sistema funciona. No tiene problemas críticos. Los usuarios están acostumbrados. Pero comparado con lo que la tecnología moderna puede hacer, está dejando dinero sobre la mesa todos los días. La pregunta no es "¿está roto?" sino "¿está compitiendo?"

El argumento para el CEO de un sistema que "funciona bien"
"Su sistema funciona. Pero su competidor que migró hace 2 años está tomando mejores decisiones con IA, lanzando funciones 6 meses antes que ustedes y cobrando en mobile mientras sus vendedores necesitan ir a la oficina. El sistema no está roto — está perdiendo la carrera. No se migra porque está roto. Se migra para no quedar fuera de la cancha."
El costo de oportunidad — lo que se pierde cada mes sin migrar
Cómo cuantificar lo que cuesta no modernizarse
▼
  • Time to Market lento: Cada feature que tarda 6 meses en un sistema legacy podría tardar 2 semanas en cloud con microservicios. Si el negocio lanza 4 features por año vs. la competencia que lanza 20, la brecha se amplía exponencialmente.
  • Talento que no viene: Los desarrolladores modernos no quieren trabajar en COBOL o VB6. El sistema legacy limita la capacidad de atraer y retener talento tecnológico.
  • Datos que no se usan: El sistema genera datos valiosos pero en formatos propietarios que no pueden alimentar analítica moderna. La empresa tiene oro en datos pero no puede refinarlo.
  • Experiencia de cliente degradada: Los usuarios comparan con Netflix, Mercado Libre y sus apps bancarias. Un sistema sin mobile, sin self-service y sin tiempo real se percibe como señal de empresa anticuada.
✅ La pregunta correcta para el CEO: "Si su competidor directo pudiera lanzar un producto nuevo en 2 semanas y ustedes tardan 6 meses, ¿cuánto tiempo más pueden mantener la misma cuota de mercado?"

04 — Las 7 Rs de migración — estrategias para cada sistema
De "mover tal cual" a "reescribir desde cero" — la estrategia correcta según el contexto
▼

No todos los sistemas se migran igual. AWS definió el framework de las 7 Rs para clasificar la estrategia de migración correcta según el estado del sistema, el presupuesto disponible y los objetivos del negocio. Una migración bien diseñada combina diferentes estrategias para diferentes sistemas.

Las 7 estrategias en detalle
Retire · Retain · Rehost · Replatform · Repurchase · Refactor · Rebuild — con ejemplos y cuándo aplicar cada una
▼
1R
Retire (Retirar)
Apagar
El sistema ya no tiene usuarios activos o su función fue absorbida por otro sistema. La mejor migración es no migrar — apagarlo directamente.
Ej: Un sistema de gestión de turnos reemplazado por un módulo del nuevo ERP. El legacy tiene 3 usuarios ocasionales. → Apagar.
2R
Retain (Retener)
Mantener por ahora
El sistema tiene demasiada complejidad para migrar ahora o hay una razón de negocio para mantenerlo on-premise temporalmente. Se deja donde está y se define una fecha futura de migración.
Ej: Mainframe bancario con auditoría regulatoria en 6 meses. → Mantener hasta después de la auditoría.
3R
Rehost (Lift & Shift)
Mover tal cual
Mover el sistema a la nube sin ningún cambio de código. La VM on-premise se convierte en una VM cloud. Más rápido y barato. Menor valor inicial pero elimina el riesgo de hardware.
Ej: 20 VMs con Windows Server en DC propio → migrarlas a Personal Tech Cloud con misma configuración. Sin tocar el código.
4R
Replatform (Lift, Tinker & Shift)
Mover + mejoras menores
Mover con optimizaciones menores que aprovechan el cloud sin reescribir la lógica del negocio. Cambiar MySQL en VM por RDS, o el servidor de archivos por S3.
Ej: App PHP en servidor dedicado → App en EC2 con RDS en lugar del MySQL local. Sin cambiar el código PHP.
5R
Repurchase (Drop & Shop)
Reemplazar por SaaS
Abandonar el sistema legacy y reemplazarlo con un producto SaaS moderno. El CRM hecho a medida en 2008 se reemplaza por Salesforce o HubSpot.
Ej: Sistema de gestión de clientes hecho a medida en Delphi → Salesforce CRM. Se migran los datos, no el código.
6R
Refactor / Re-architect
Rediseñar para cloud
Reestructurar el código para aprovechar capacidades cloud nativas: microservicios, serverless, contenedores. Mayor inversión inicial, mayor valor a largo plazo.
Ej: Monolito Java en servidor único → microservicios en Kubernetes con auto-scaling y CI/CD. El negocio sigue, la arquitectura cambia.
7R
Rebuild / Rewrite
Construir desde cero
El sistema es tan legacy que es más barato y eficiente construirlo nuevo que migrarlo. Se reimplementa la lógica del negocio con tecnología moderna cloud-native.
Ej: Sistema COBOL de 40 años donde el código no tiene documentación ni tests. Se rediseña desde cero en microservicios con APIs modernas.
✅ Regla práctica: en un proyecto típico de migración de 20+ sistemas, la distribución suele ser: 10–20% Retire, 5–10% Retain, 50–60% Rehost/Replatform, 15–20% Repurchase, 5–10% Refactor/Rebuild. Empezar por los Rehost — dan resultados rápidos y construyen confianza para las estrategias más complejas.
El camino de migración paso a paso
Del relevamiento inicial al go-live — las fases de un proyecto de migración bien ejecutado
▼
1
Discovery y Assessment (semanas 1–3)
Relevamiento completo del portfolio de aplicaciones. Para cada sistema: tecnología, versión, usuarios activos, dependencias, criticidad del negocio, costo de mantenimiento. Output: mapa de aplicaciones con estrategia 7R asignada a cada una.
2
Diseño de la arquitectura cloud destino (semanas 3–5)
Diseñar la arquitectura objetivo: qué cloud (Personal Tech / público / híbrido), tamaños de instancias equivalentes, seguridad, red, DR. Output: arquitectura cloud documentada y aprobada.
3
Migración por olas — no críticos primero (semanas 5–10)
Ola 1: entornos de desarrollo, backup, web. Sin impacto si algo falla. Ola 2: sistemas de soporte (RRHH, facturación secundaria). Ola 3: sistemas críticos del negocio (ERP, core). Cada ola valida el proceso antes de la siguiente.
4
Testing y validación (paralelo con cada ola)
El sistema cloud corre en paralelo con el on-premise durante 2–4 semanas. Se comparan resultados, rendimiento y disponibilidad antes de hacer el cutover definitivo.
5
Cutover y go-live (semana 10–16)
Cutover del sistema crítico en horario de bajo tráfico. Plan de rollback documentado y probado. Hipercare por 2–4 semanas con soporte prioritario. El on-premise se apaga gradualmente, no de golpe.
6
Optimización post-migración (meses 4–6)
FinOps: rightsizing, reservas, eliminación de zombies. Monitoreo y ajuste de rendimiento. Documentación de la arquitectura final. El 30% del ahorro total del cloud se captura en esta etapa.

05 — Nube privada vs. nube pública vs. híbrida
La decisión de arquitectura más importante de cualquier proyecto de migración
▼

La elección entre nube privada, pública o híbrida no es una decisión técnica — es una decisión de negocio que combina consideraciones de costo, seguridad, compliance, control y estrategia. Personal Tech puede dar los tres modelos, lo que es una ventaja única frente a cualquier hyperscaler.

Comparativa completa
Nube privada · Pública · Híbrida · Multi-cloud — definiciones, ventajas y cuándo elegir cada una
▼
ModeloDefiniciónVentajasDesventajasIdeal para
Nube privada Infraestructura cloud dedicada exclusivamente a una organización. Puede ser on-premise (en el DC de la empresa) o hosted en el DC de un proveedor como Personal Tech. Máximo control y personalización. Dato soberano. Cumplimiento regulatorio simplificado. Rendimiento predecible sin "noisy neighbors". Mayor costo por recursos no compartidos. Escalado tiene límite de la infraestructura dedicada. Requiere más gestión. Banca, salud, gobierno, empresas con datos muy sensibles o regulados. Clientes de Personal Tech en Pacheco.
Nube pública Infraestructura compartida entre múltiples clientes del mismo proveedor (AWS, Azure, GCP). El cliente alquila recursos virtuales del pool compartido. Escalado prácticamente ilimitado. Pay-as-you-go. Acceso a 200+ servicios avanzados (IA, analytics, serverless). Sin CAPEX. Datos fuera del país. Menor control. Costos pueden crecer sin FinOps. Egress fees. Compliance más complejo. Startups y scale-ups. Workloads con picos de tráfico muy variables. Empresas que necesitan servicios de IA/ML avanzados.
Nube híbrida Combinación de nube privada y pública conectadas por red privada (MPLS o Direct Connect). Cada workload va al modelo más adecuado. Lo mejor de ambos mundos. Datos críticos en privada, workloads variables en pública. Sin lock-in completo. Flexibilidad total. Mayor complejidad de gestión. Requiere conectividad de alta calidad entre los dos mundos. Costos de integración. Empresas con mezcla de workloads: algunos regulados (privada) y otros variables o de IA (pública). El modelo más común en enterprise.
Multi-cloud Uso de múltiples proveedores de nube pública simultáneamente (AWS + Azure + GCP + Personal Tech). Cada servicio en el proveedor donde mejor funciona. Sin vendor lock-in. Mejor servicio para cada caso de uso. Resiliencia ante caídas de un proveedor. Negociación de precios. Mayor complejidad operativa. Múltiples contratos y consolas. Requiere equipo IT muy maduro o herramienta de gestión multi-cloud. Grandes corporaciones con equipos DevOps maduros. Empresas con necesidades muy específicas por vertical (IA en GCP, datos en Personal Tech, aplicaciones en Azure).
✅ La propuesta de Personal Tech: Personal Tech puede ser el proveedor de nube privada soberana (datos en Argentina, compliance BCRA) y simultáneamente ofrecer conectividad privada a AWS y Azure (como partner de Direct Connect y ExpressRoute). El cliente tiene cloud híbrida con un solo proveedor responsable de la conectividad entre todos los mundos.

06 — Virtudes estratégicas de la modernización
Por qué las empresas que migran y se mantienen actualizadas ganan la carrera competitiva
▼

La modernización tecnológica no es un proyecto IT — es una decisión estratégica de negocio. Las empresas que mantienen sus sistemas actualizados no solo ahorran en costos de IT — compiten en una categoría diferente. La velocidad, la inteligencia y la resiliencia que da la infraestructura moderna se traducen directamente en ventaja competitiva.

Las 8 virtudes estratégicas de migrar y mantenerse actualizado
De la velocidad al mercado a la atracción de talento — el impacto real en el negocio
▼
⚡
Velocidad al mercado (Time to Market)
Con CI/CD, microservicios y cloud nativo, el ciclo de lanzamiento pasa de meses a semanas. En industrias donde el primero que llega gana, esta diferencia define quién lidera el mercado. Amazon despliega software cada 11 segundos. No es magia — es arquitectura moderna.
🧠
IA y analítica como ventaja competitiva
Un sistema cloud moderno puede integrar IA predictiva en semanas usando APIs de Bedrock, Azure OpenAI o Vertex AI. El sistema legacy requiere años y millones. La empresa que predice la demanda, personaliza la oferta y automatiza decisiones gana sobre la que opera por intuición.
🌱
Escalabilidad sin límite
El negocio puede crecer sin decirle a IT que compre más hardware. Un pico de demanda se absorbe automáticamente. Una expansión a nuevas regiones no requiere construir un DC — se activa en minutos. La infraestructura deja de ser un freno para el crecimiento.
🛡
Seguridad moderna y proactiva
Los sistemas cloud modernos tienen Zero Trust, encriptación nativa, detección de amenazas con IA y parches automáticos. El sistema legacy tiene firewalls de perímetro y parches que nunca llegan. En el contexto de ransomware actual, esto es la diferencia entre sobrevivir y quedar fuera del negocio.
💰
Modelo financiero CAPEX → OPEX
Pasar de inversión de capital (servidores, licencias) a gasto operativo predecible (suscripción mensual) mejora el flujo de caja y la flexibilidad presupuestaria. En Argentina, donde el CAPEX en dólares es especialmente doloroso, este cambio tiene valor financiero adicional.
🔄
Resiliencia y continuidad garantizadas
Multi-región, failover automático, RTO en minutos vs. horas. Un desastre (incendio, inundación, ransomware) que destruiría un DC on-premise es un incidente menor en una arquitectura cloud bien diseñada. La continuidad del negocio deja de depender de un rack físico.
👥
Atracción y retención de talento
Los mejores desarrolladores y arquitectos quieren trabajar con Kubernetes, microservicios, serverless y cloud nativo — no con COBOL y VB6. Una empresa con stack moderno atrae mejores perfiles y los retiene más tiempo. El talento tecnológico es el recurso más escaso del mercado.
🌍
Expansión geográfica sin fricción
Abrir operaciones en una nueva ciudad, provincia o país no requiere instalar servidores locales. Con cloud, la expansión es una configuración. Una empresa argentina puede servir a clientes en toda Latinoamérica desde el mismo stack cloud en horas.
El argumento estratégico definitivo para el CEO
"En 5 años, las empresas de su industria van a dividirse en dos grupos: las que aprovecharon la ventana de modernización tecnológica de 2024–2026 y las que no. Las primeras van a competir con IA, escalar sin límite y lanzar productos en semanas. Las segundas van a estar pagando consultores COBOL y rogando que el servidor de 2008 no se rompa. Personal Tech es el puente a ese primer grupo."

07 — Cómo proponer la migración al cliente
El discurso correcto según el interlocutor — CEO, CTO, CFO, Gerente de Planta
▼
Argumentos por tipo de interlocutor
Cada persona en la organización tiene un dolor diferente — el mismo proyecto, distintos argumentos
▼
👔
Para el CEO
Su lenguaje: mercado, competencia, crecimiento.
Argumento: "Su competidor que migró hace 2 años lanza funciones 6 meses antes. La modernización no es un gasto — es la apuesta por seguir siendo relevante en su industria en 5 años."
💰
Para el CFO
Su lenguaje: costos, presupuesto, riesgo financiero.
Argumento: "CAPEX en hardware dolarizado en año 3 vs. OPEX predecible en pesos. El cloud no es más caro — es predecible. Y predecible en Argentina vale mucho."
🖥
Para el CTO / Director IT
Su lenguaje: arquitectura, deuda técnica, disponibilidad.
Argumento: "Cada año que no migramos, la deuda técnica crece. Su equipo pasa el 70% del tiempo apagando incendios del sistema viejo. Con cloud, ese tiempo se invierte en proyectos que hacen crecer el negocio."
⚙️
Para el Gerente de Operaciones
Su lenguaje: continuidad, disponibilidad, no complicar lo que funciona.
Argumento: "La migración se hace en paralelo — el sistema viejo sigue funcionando hasta que el nuevo esté validado. No hay riesgo de corte. Y después, las caídas de 2am son problema de Personal Tech, no de usted."
⚠️ La regla más importante: Nunca presentar la migración como "cambiar lo que funciona" — siempre como "agregar capacidades que hoy no tienen". El cerebro humano resiste el cambio pero acepta las mejoras.
Las preguntas de discovery para sistemas legacy
Las 6 preguntas que revelan el dolor y abren la conversación de migración
▼
  • "¿Cuándo fue la última vez que actualizaron el sistema core y cuánto tardó la actualización?" → Revela el ciclo de release lento y el riesgo de cada cambio.
  • "Si el único desarrollador que conoce el sistema renunciara mañana, ¿qué pasaría?" → La respuesta siempre genera incomodidad. Eso es el dolor real.
  • "¿Cuánto tarda en agregar una nueva funcionalidad que el área comercial pide?" → Cuantifica el Time to Market y la fricción entre IT y negocio.
  • "¿Tienen visibilidad de qué tan cerca están del límite de capacidad de sus servidores?" → Muchos no lo saben. La respuesta es "no, esperamos que no se cuelgue".
  • "¿Pudieron hacer una prueba de DR en los últimos 12 meses? ¿Cuánto tardaron en recuperar el sistema?" → La mayoría no tiene prueba documentada. Revela el riesgo de continuidad.
  • "¿Cuánto invierten hoy en mantener el sistema viejo vs. en proyectos nuevos?" → La respuesta usual: 70–80% en mantenimiento, 20–30% en innovación. El cloud invierte esa ecuación.

08 — Glosario técnico A–Z — Legacy, Migración y Modernización
Todos los términos clave definidos en lenguaje claro para reuniones técnicas y ejecutivas
▼
A – D
API · Application Portfolio · CAPEX vs OPEX · CI/CD · Cloud Native · Contenedores · Deuda técnica
▼
A
API
Application Programming Interface
Interfaz que permite que dos sistemas de software se comuniquen entre sí de forma estandarizada. Es el "enchufe universal" del software moderno. Un sistema sin API es un sistema que no puede integrarse con el mundo.
El sistema legacy de facturación no tiene API → cada integración nueva requiere un proyecto de meses. Un sistema moderno con API REST integra en días.
C
CAPEX / OPEX
Capital Expenditure / Operational Expenditure
CAPEX: gasto de capital. Compra de servidores, hardware, licencias perpetuas. Se activa como activo fijo y se deprecia. Gran desembolso inicial. OPEX: gasto operativo. Suscripción mensual al cloud. Se registra como gasto corriente. Sin shock de capital.
Comprar $200K de servidores = CAPEX. Pagar $8.000/mes al cloud = OPEX. En Argentina, el OPEX en pesos predecible tiene valor adicional frente al CAPEX dolarizado.
C
CI/CD
Continuous Integration / Continuous Deployment
Pipeline automatizado que toma el código del desarrollador, lo prueba automáticamente y lo despliega en producción. Permite lanzar software de forma segura múltiples veces por semana. Imposible con sistemas legacy que requieren releases manuales.
Con CI/CD: cada cambio de código se prueba en 10 minutos y se despliega solo si pasan todos los tests. Sin CI/CD: un release requiere 2 semanas de coordinación y testing manual.
C
Cloud Native
Cloud Native
Aplicaciones diseñadas desde el principio para correr en cloud, aprovechando sus capacidades: microservicios, contenedores, serverless, escalado automático. A diferencia de aplicaciones "cloud hosted" (on-premise movida a cloud), las cloud native se diseñan pensando en el cloud.
Netflix es cloud native: escala automáticamente para millones de usuarios simultáneos. Un ERP legacy movido a cloud en VM es cloud hosted — no aprovecha casi nada.
C
Contenedores (Docker)
Containers
Unidad estandarizada de software que empaqueta el código y todas sus dependencias para que la aplicación corra de forma rápida y confiable en cualquier entorno. Más ligeros que VMs, más portables que código instalado directamente.
El mismo contenedor Docker corre idéntico en la laptop del dev, en CI/CD y en producción cloud. Elimina el "en mi máquina funciona".
D
Deuda Técnica
Technical Debt
El costo implícito de elegir una solución de desarrollo rápida en lugar de una mejor solución que tomaría más tiempo. Como la deuda financiera, si no se paga crece con intereses — cada modificación futura es más lenta y costosa.
Código sin tests, sin documentación, con lógica duplicada. El sistema "funciona" pero cada cambio tarda 3 veces más de lo normal porque el desarrollador tiene miedo de romper algo.
E – M
EOL · Failover · IaC · Kubernetes · Legacy · Lift & Shift · Microservicios · Monolito
▼
E
EOL / EoS
End of Life / End of Support
Fecha a partir de la cual el fabricante deja de publicar actualizaciones de seguridad para un producto. Usar software en EOL es aceptar vulnerabilidades conocidas sin solución.
Windows Server 2012: EOL en octubre 2023. PHP 7.4: EOL en noviembre 2022. Correr estos sistemas en producción es un riesgo de seguridad documentado.
F
Failover
Failover
Proceso automático por el cual un sistema cambia a una instancia de respaldo cuando la principal falla. Un buen failover es transparente: el usuario no nota la caída.
El servidor principal falla a las 3am. El failover automático activa el servidor de DR en 90 segundos. Los usuarios de guardia no notan interrupción.
I
IaC
Infrastructure as Code
Práctica de gestionar y aprovisionar infraestructura mediante archivos de código en lugar de procesos manuales. Toda la infraestructura está versionada, revisable y reproducible. Terraform, CloudFormation, Pulumi.
El datacenter completo (redes, servidores, bases de datos, seguridad) está descrito en archivos YAML. Se destruye y recrea idéntico en 20 minutos con un comando.
K
Kubernetes (K8s)
Kubernetes
Sistema de orquestación de contenedores que automatiza el despliegue, escalado y gestión de aplicaciones. Permite que miles de contenedores funcionen como un sistema coherente y autoreparable.
Si un contenedor falla, Kubernetes lo detecta y lanza uno nuevo automáticamente. Si el tráfico sube, agrega contenedores. Si baja, los elimina. Sin intervención humana.
L
Legacy System
Sistema heredado / obsoleto
Sistema de software o hardware que está en uso pero se considera obsoleto debido a su tecnología, falta de soporte o dificultad de mantenimiento. No necesariamente viejo en años — puede ser joven pero construido con mala arquitectura.
Un ERP construido en 2015 con arquitectura monolítica, sin tests, sin API y con un único desarrollador que lo conoce — ya es legacy a pesar de su edad.
M
Microservicios
Microservices
Arquitectura donde una aplicación se divide en servicios pequeños e independientes, cada uno con una responsabilidad específica y comunicado con los demás via APIs. Opuesto al monolito. Permite escalar, actualizar y desplegar partes independientemente.
El servicio de autenticación escala independientemente del servicio de facturación. Si el de facturación falla, el de autenticación sigue funcionando.
M
Monolito
Monolithic Architecture
Arquitectura donde toda la aplicación es un único bloque de código que se despliega completo. Funciona bien al principio pero escala mal. Un bug en cualquier módulo puede tumbar toda la aplicación.
El ERP de 2005 donde el módulo de inventario, el de facturación, el de RRHH y el de ventas son el mismo ejecutable. Para actualizar los sueldos hay que correr el riesgo de afectar las facturas.
O – Z
On-premise · Orquestación · Refactoring · Rollback · RPO/RTO · Serverless · Shadow IT · VM · Zero Trust
▼
O
On-Premise
On-Premise / In-House
Infraestructura tecnológica instalada físicamente en las instalaciones de la propia empresa. El hardware está en la sala de servidores del cliente. Mayor control pero también mayor responsabilidad operativa y costo de mantenimiento.
Los 20 servidores en el rack del cuarto de comunicaciones del edificio corporativo. El equipo IT los gestiona, parchea y reemplaza cuando fallan.
R
Refactoring
Refactoring / Reestructuración
Proceso de reestructurar el código existente sin cambiar su comportamiento externo. El objetivo es mejorarlo: hacerlo más legible, mantenible, eficiente. No agrega funcionalidades — mejora la base para agregarlas en el futuro.
Dividir una función de 2.000 líneas en 20 funciones de 100 líneas cada una. El sistema hace lo mismo, pero ahora cualquier desarrollador puede entenderlo.
R
Rollback
Rollback
Capacidad de volver a una versión anterior del sistema cuando un despliegue introduce un problema. En sistemas legacy, el rollback puede tardar horas o ser imposible. En cloud moderno con CI/CD, es un comando.
Se despliega una versión nueva del ERP. Hay un bug crítico. Rollback en 2 minutos a la versión anterior sin pérdida de datos.
R
RPO / RTO
Recovery Point/Time Objective
RPO (Recovery Point Objective): cuántos datos puede permitirse perder en un desastre (ej: máximo 1 hora de datos). RTO (Recovery Time Objective): cuánto tiempo puede estar el sistema caído antes de recuperarse (ej: máximo 4 horas).
RPO 1 hora + RTO 4 horas significa: el sistema debe estar recuperado en 4 horas y no perder más de 1 hora de transacciones. Un legacy sin DR puede tener RTO de días.
S
Serverless
Serverless Computing
Modelo de ejecución donde el desarrollador escribe funciones de código y el proveedor cloud gestiona toda la infraestructura: servidores, escalado, parches. Se paga solo cuando el código se ejecuta — nada cuando no hay tráfico.
AWS Lambda: una función que procesa facturas corre solo cuando llega una factura. Si llegan 10 o 10.000 simultáneas, escala sola. Si no llegan, cuesta $0.
S
Shadow IT
Shadow IT
Sistemas o aplicaciones usados dentro de una organización sin aprobación o conocimiento del área de IT. Síntoma típico de sistemas legacy que no satisfacen las necesidades del negocio. Los usuarios buscan alternativas por su cuenta.
El equipo comercial usa Google Sheets compartido para gestionar oportunidades porque el CRM legacy es demasiado lento. IT no lo sabe. Los datos están dispersos y sin backup.
V
VM / Máquina Virtual
Virtual Machine
Emulación de un sistema informático completo que corre sobre hardware físico compartido. Permite correr múltiples sistemas operativos en un mismo servidor. Base de la virtualización cloud.
Un servidor físico con 64 cores puede correr 20 VMs independientes de 3 cores cada una. Cada VM cree que tiene su propio servidor.
Z
Zero Downtime Migration
Migración sin interrupción
Técnica de migración donde el sistema viejo y el nuevo corren en paralelo, con tráfico enrutado gradualmente al nuevo. El usuario final no experimenta ninguna interrupción durante la migración.
El 10% del tráfico va al sistema cloud nuevo mientras el 90% sigue en el legacy. Gradualmente se aumenta al 20%, 50%, 100% a medida que se valida la estabilidad.
